# AI 测试人员项目评审

日期：2026-09-16 · 评审对象：本次对话形成的产品方案，无现有代码库或客户运行数据

## 1. 结论

**建议进入有边界的技术验证与客户试点，不建议直接以“完全无人值守替代整个测试岗位”作为首版交付承诺。**

定位保留：承担需求驱动的独立测试，重点验收多人开发合并后的业务流程。开发者已经检查代码并不保证跨模块行为、权限与数据流符合产品要求，这正是产品要验证的对象。

可复用的浏览器执行与智能操作组件已经存在；项目价值将主要体现在业务规则提取、可靠判定、测试数据管理和缺陷证据上。商业价值仍需客户试点确认，当前没有付费意愿、节省工时或可靠性实测证据。

## 2. 原方案需要修正的地方

| 问题 | 对开发的影响 | 本次修正 |
|---|---|---|
| “替代测试人员”范围过大 | 容易同时承诺 UI、接口、安全、性能、移动端 | 首版聚焦后台 Web 的需求验收、跨角色流程、合并后回归 |
| 从资料直接跳到浏览器执行 | 预期结果容易由模型临时编造 | 先形成有来源的规则与不可变用例版本，再执行 |
| 过度依赖模型判断通过 | 容易把看到成功提示当作业务成功 | 核心状态、金额、权限使用程序化断言；模型视觉结论单独处理 |
| 账号与数据准备不具体 | 在演示站成功，接入客户环境失败 | 项目接入合同包含账号、初始化、清理、依赖系统与网络条件 |
| 所有开源组件都引入 | 浏览器状态、语言运行时与维护成本叠加 | Playwright 为主执行器，Midscene 是同一会话的视觉适配器 |
| 自动修复边界不足 | 模型删掉失败断言，得到虚假通过 | 修复只产生定位/等待候选补丁，预期结果哈希不可变化 |
| 重试与中断语义不清楚 | 重复提交产生新数据，首次失败被覆盖 | 保存每次尝试，状态不明时先核对副作用，不自动重放提交 |
| 测试结果缺少版本绑定 | 换了需求或环境后旧报告失去意义 | 绑定需求、用例、执行计划、环境构建和模型配置版本 |
| 首版六周范围偏满 | 文档解析、视觉、用例管理、执行平台可能都只完成表面 | 先完成一条真实纵向链路，随后扩展；周期按依赖和试点条件调整 |

## 3. 关键技术决策

### 决策 A：需求是验收依据

模型先从产品资料生成规则与用例，后从页面学习执行方法。当前系统行为与源代码都不能自动覆盖需求。原型没有说明的金额边界、权限和状态规则必须标为未知。

### 决策 B：运行时使用受限制的测试计划

首版采用结构化 TestPlan，由受控执行器完成导航、输入、点击、角色切换与断言。模型不能向服务端提交任意 JavaScript 并直接执行。后续可由平台把计划导出为 Playwright 测试代码。

这是有意收窄的实现选择：减少“模型生成代码在服务器任意运行”的工程负担，并让执行步骤、权限和预期结果可审查。可选 Codex 集成用于生成测试资产或诊断，不是首版必要依赖。

### 决策 C：浏览器框架只设一个主要所有者

Playwright 管理生命周期、每角色 BrowserContext、证据和断言；Midscene 复用当前页面处理视觉步骤。Browser Use 暂不纳入首版。这里的取舍针对本项目复杂度，不代表框架质量排名。

### 决策 D：状态与结论分开

任务正常结束不代表测试通过。分别存执行生命周期、业务判定和失败原因；环境失败、模型失败、待澄清、被跳过都不能计为通过。

## 4. 可行性与主要风险

| 方面 | 判断 | 需要验证的证据 |
|---|---|---|
| 浏览器操作 | 有成熟组件可复用 | 两个角色完成目标站的一条真实流程 |
| 资料到规则/用例 | 能开发，完整性和准确性未验证 | 与人工确认规则和用例对比，检查遗漏与无依据扩写 |
| 业务正确性判定 | 本项目最重要的难点 | 在已知 Bug 与健康版本上都运行，统计检出和误报 |
| 私有系统接入 | 工程量容易低估 | 真实登录、网络、数据重置、审批和异步依赖能否处理 |
| 重复执行 | 能做，但必须有状态隔离 | 同版本干净数据重复运行的结果一致率 |
| 成本 | 无实测，不能承诺单轮价格 | 按模型、截图量、动作数和耗时记录真实用量 |
| 商业化 | 有明确问题假设，尚未验证付费 | 客户愿意持续使用，确认节省时间并提出采购条件 |

最大风险不是“点不到按钮”，而是“没有充分依据却判为通过”。第二大风险是把测试环境、数据和账号问题全部交给模型临时猜测。

## 5. 第一批客户与试点选择

优先寻找具有以下条件的团队：有 Web 管理后台；多人并行开发；每次发版都有人重复跑审批或订单链路；已有至少部分产品文档；可以提供隔离测试环境和角色账号。

建议选择一个审批业务试点，覆盖申请人、审批人两种角色及至少两个业务模块。用客户真实流程检验收益，不能只靠我们自己搭建的演示站证明泛化能力。

首版交付承诺建议写为：**根据确认的产品规则自动执行选定流程，提供可追溯报告、未验证范围和缺陷复现证据。**

## 6. 投入与阶段门槛

假设 2 名具备全栈/自动化经验的工程师，以及能定期响应的产品负责人；AI 编程工具是提效手段，不计作替代上述能力的保证。

- 第 1–2 周：工程骨架与最小纵向闭环，人工确认的少量规则执行到真实演示站。
- 第 3–4 周：资料解析、真实 GLM、结构化计划、两角色执行与可靠结果判定。
- 第 5–6 周：版本、证据、缺陷复测、异常恢复、真实客户接入。
- 预留第 7–8 周：处理客户登录、文档质量、环境与视觉适配的差异。

以上是估算，不是固定交期。优先交付 PRD 中的 P0，P1 不得挤占真实闭环。

### Go / 调整 / 暂停条件

1. **继续**：真实试点可完整运行；已知缺陷和健康版本均有结果；人工介入时间下降且报告可信。
2. **调整范围**：操作可完成，但误报集中在某类视觉判断或环境条件，缩小自动判定范围并保留待确认。
3. **暂停扩展**：关键业务缺陷反复被判为通过、清理数据无法控制、客户持续需要逐步骤救场。先解决这些问题再做功能扩张。

初步效果目标见 PRD；所有比例必须带分子、分母、版本与未覆盖范围。小样本成功不能外推为“替代所有测试人员”。

## 7. 可复用项目与证据

- [Playwright Test Agents](https://playwright.dev/docs/test-agents)：提供规划、生成与修复角色。它是可复用流程，不是完整的需求验收产品；官方说明 healer 可能输出跳过测试，产品不能把跳过记为通过。
- [Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer)：可查看动作、页面快照和网络等执行信息，适合作为缺陷证据来源。原始 trace 可能含敏感数据，必须限制访问。
- [Midscene](https://www.midscenejs.com/introduction)：提供视觉驱动操作和测试工具，可作为执行层补充。
- [Midscene 模型配置](https://www.midscenejs.com/model-common-config)：模型能力与接入按实际安装版本核对。
- [智谱工具调用](https://docs.bigmodel.cn/cn/guide/capabilities/function-calling)：模型返回工具调用请求，真正的执行和参数校验由应用负责。

核验日期：2026-09-16。项目能力说明来自官方资料；本次未安装或实测这些框架，没有对供应商模型进行性能排名。浏览器能力和文档可用不等于目标网站上的测试有效性已经得到证明。
