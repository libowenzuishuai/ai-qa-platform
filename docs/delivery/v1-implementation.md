## 2. 判定规则与本轮发现的问题

- 预期来自批准用例；模型只能建议执行动作与已有目标引用。不能修改业务预期、发明定位器或批准自己的计划。mock 计划不得批准用于真实验收。
- 计划按环境配置版本绑定。账号/环境配置发生变化后必须重新观察和批准。
- 复测固定原计划 ID 与验收哈希；相同幂等键不能借复测切换标准。
- 构建核验在执行前后读取同源部署查询端点，并保存带校验和的证据。声明版本本身不够；核验或完整范围不满足时不能整体 PASS。该机制信任部署查询端点，不是密码学构建来源证明。
- API 数值比较的预期/实际顺序已修正，并补充非对称操作符回归。
- 真实 Kimi 的第一次尝试遗漏等待目标，被平台拒绝；第二版建议等待“业务成功”后才断言，导致故障被记为未完成。第三版禁止模型生成这类前置等待，改为断言内有界只读重试；最终业务不符记 FAIL，不重放写入。默认生成计划的读取重试窗口为 2.5 秒，不代表业务 SLA。
- 凭据值不保存在业务配置中。项目管理员只能登记当前项目命名空间的 `AIQA_TARGET_<项目哈希>_...` 环境变量名；项目页面显示具体前缀。普通通用环境没有演示账号回退。
- 工程测试结果与业务验收分开。无用例、只有跳过、失联、过期租约或缺少证据不能伪装成通过。

## 4. 使用方式

1. 按根 README 与 Python 服务说明配置本地环境。API/worker/Python 应使用同一证据目录，内部服务令牌一致，默认 `AIQA_INTELLIGENCE_BACKEND=python`。
2. 更新依赖后执行 `pnpm --filter @ai-qa/api db:generate`、`pnpm db:migrate`。新增迁移 `20260920140000_product_workflow` 为加表/加字段，不要求重置数据库。
3. 分别启动 API（7300）、worker（7200）、Python 智能服务（7500）和 web（7100）。进程启动前须注入各自环境变量；不要把密钥提交到 Git。
4. 登录 web → 创建/选择项目 → 项目空间接入仓库和测试网址 → 产品上下文确认资料、解析、提取规则、生成用例。
5. 审阅批准规则和用例；在能力与集成配置测试账号引用、构建查询接口；观察实际页面，生成并确认执行计划，建立基线、创建任务、填写实际构建 ID 后启动。
6. 交付评估查看结果、处理缺陷、新构建复测。工程检查的运行器配置见 [运行器说明](../../tools/self-hosted-runner/README.md)。

测试会创建并清理独立数据库、队列、端口与证据目录；本次没有自动迁移或重启用户日常开发实例。

## 5. 尚未完成的产品能力

- 外部真实客户项目试点、重复稳定性、检出率/误报率、人工介入成本和负载评测。
- 任意仓库一键部署、多服务依赖编排、私有 GitHub/GitLab、CI webhook 自动触发、复杂测试框架适配。当前 Node 构建只产出构建结果，不提供自动部署 URL。
- 完全自主的登录探索、通用测试数据准备/回收插件、多角色复杂流程的新增真实模型验收。通用观察的准备动作需明确配置，持久化写入的清理由项目负责人安排。
- 自动需求变更影响分析、回归选择、可拖拽组装智能体 harness、视觉自由操作、移动端、性能/安全测试。
- 完整断言编辑表单、原型视觉还原、任务模板的独立策略引擎。目前模板复用同一受限执行链，用户选择批准基线。
- 平台 api/web/worker 完整容器化部署仍未重新验收；此次主要验收宿主服务 + PostgreSQL/Redis/Docker runner。

下一步优先接入一个外部真实项目，走完整资料→规则→用例→计划→执行→修复复测，并据此收敛接入向导与数据准备能力。
