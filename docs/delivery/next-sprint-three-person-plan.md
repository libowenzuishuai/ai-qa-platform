# 下一阶段三人分工：真实项目试点与 1.0 交付闭环

日期：2026-09-20。代码基线：`f1da1eb`（前四步基础能力）。三个人从包含本文的最新 `main` 开新分支。本文接替阶段二开工清单中的“下一步任务”，不要求重做已合入模块。

## 一、下一步做什么

**本轮目标：一个真实项目从原始需求资料走到修复复测，第二个不同业务项目复验；把接入所需的人工步骤变成清晰的产品流程。**

当前已有的两类合成业务验证了真实 Kimi 计划生成与浏览器执行，但规则/用例由人工预置。资料解析、规则生成、代码运行器也有各自验证，尚不能据此宣称真实项目整链已验收。下一轮补这条证据链，不先扩大功能清单。

对照 PRD：

| PRD 要求 | 现在 | 本轮补齐 | 主责 |
|---|---|---|---|
| FR-CTX-01/02 仓库资料与可信来源 | Git 发现、分类、导入、来源机制已接通 | 真实复杂文档的正文/表格/图片依据能回到原文，遗漏可见 | B |
| FR-CTX-03 资料更新 | 已有快照与文件增删改列表 | 提供片段变化与来源映射建议；平台显示受影响资产并要求复核 | B 提供依据；C 分析建议；A 接线 |
| FR-TASK-01/02/03 任务与资产 | 基线任务、批准冻结、基础编辑已实现 | 接入向导、完整断言编辑、准备缺口；真实资料生成的用例实际执行 | A + C |
| FR-RUNNER-01/02/03 执行 | Web/API、Node/pytest、自有运行器模块可运行 | 真实 Git 提交→自有运行器→报告；账号/数据准备、失败清理、取消回收 | A |
| FR-RESULT-01/02 与发布门槛 | 缺陷、证据、原标准复测已接通 | 真实项目完整链与重复稳定性、成本、人工介入记录 | 三人联合，A 汇总 |

本轮先走“已有测试网址 + 业务资料”路径。源码自动部署、单服务 Node + PostgreSQL 模板仍是后续独立里程碑，不在此轮偷偷承诺。

|---|---|---|---|
| A / 李博闻 | 用户能完成接入与执行，平台能可靠解释结果；总集成与发布验收 | `apps/api`、`apps/worker`、`apps/web`、`packages/test-runtime`、`packages/reporting`、`tools/self-hosted-runner` | `v1/pilot-platform` |
| B / 原泽菲 | 原始业务资料被准确理解为有来源的片段；变更不会丢失依据 | Python `doc_ingestion`、`tests/doc_ingestion`；新增独立 `source_changes` 模块和对应测试（如需要） | `v1/document-fidelity` |

## 三、A / 李博闻任务（按依赖顺序）

### A0：准备试点与冻结接口

- 选一个允许测试的真实项目，固定需求版本、部署版本、账号权限、允许写入范围和清理办法；第二个业务项目作为发布复验。
- 建立同一份验收清单：关键用户旅程、人工确认的预期、健康版本、已知或专门注入的缺陷版本、修复版本。答案只给评测器，不能进入模型上下文。
- 优先沿用现有 ParsedDocumentBundle/RuleVersion/TestCaseVersion/TestPlan。确需增加来源变化、准备状态等字段时，A 先提交最小契约及正反例，再让 B/C 接入。
- 提供 B/C 可独立使用的脱敏输入和已观察页面数据。外部项目尚未到位时先用合成夹具继续开发，报告必须标明真实试点尚未完成。

### A1：把已有页面串成接入向导

- 项目接入 → 确认资料 → 审阅规则/用例 → 账号与数据检查 → 执行计划确认 → 开始验收。保留七个导航页，但首屏给出当前状态与下一动作。
- 用例编辑补齐前置条件、角色、数据、步骤、断言预期和清理方式；保存生成新版本，已批准旧版不变。
- 显示缺少什么、由谁补、补完如何继续；不要求普通用户输入内部数据库 ID 或手写执行 JSON。
- 展示任务预算、未验证范围和真实运行状态。只有准备完整、计划批准且环境版本匹配才能启动。

### A2：账号、测试数据和运行器整链

- 显式配置测试账号及准备/清理策略，按项目/运行隔离测试数据；准备失败不能继续形成业务 PASS，清理失败必须可见且不能盲目重复写入。
- 用真实公共 Git 固定提交走一次“下载 → 隔离执行 Node/pytest → 结构化结果 → 平台证据”；不得用本地源码替身冒充仓库下载成功。
- 补取消、租约失效、跨项目提交、错提交版本、空测试和重复结果反例；确认任务/容器/临时卷最终回收。
- 保持工程测试与业务验收的结论分别展示，不以代码测试通过证明 PRD 满足。

### A3：总联调与交付

- 串联 B/C 返回结果，完成全新资料→解析→规则/用例草稿→人工审阅批准→真实观察→计划→执行→缺陷→新构建复测。
- 给来源变更结果增加受影响规则/用例的待复核入口；旧任务继续使用旧版本，不自动改写标准。
- 补全启动说明、迁移说明及一次干净环境启动验证。按实际部署路径验证，不把本地进程成功写成完整容器部署成功。

**A 验收**：浏览器里能完成主路径；新用户无需直连数据库修数据；真实仓库运行器链有固定 SHA 和原始结果证据；两类业务至少各一条关键旅程完成健康/缺陷/修复对照。

## 四、B / 原泽菲任务（可立即开始）

### B1：真实资料解析与来源回看

- 覆盖 Markdown、DOCX 表格/合并单元格、混排/扫描 PDF、图片。优先处理试点资料真实遇到的结构，不先追求所有格式全支持。
- 图像内容继续使用现有 Kimi 视觉网关，不新增独立 OCR 引擎。不另存密钥、不另造 SDK。
- 金额、单位、不等号、否定词、角色和条件不得静默改写。表格中的条件与结论要保留行列关系。
- 无法可靠定位的内容保留粗粒度来源并标 LOW/UNPARSED；不要为满足契约捏造精确坐标。继续使用现有资源和页数上限。

### B2：来源变化的可追溯比较

- 对同一路径的两个明确文档版本比较新增/删除/修改片段，保留新旧文档版本与片段引用。
- 移动、重复、拆分、合并段落无法唯一对应时给出“待确认”，不能因为片段 ID 相似就断定语义未变化。
- 优先提供纯函数与独立模块，不自行新增数据库表或 HTTP 入口。若现有字段不足，提交契约提案给 A，避免改共享生成文件。
- 本模块只回答“来源哪里变了”；对业务规则的影响由 C 建议、A 按真实版本 ID 关联。

### B3：资料质量评测交付

- 建议首批至少 8 份代表性资料，覆盖正文、表格、扫描、图片和反例；数字是本轮目标，不是已完成结果。
- 每份提供预期关键片段、来源位置、遗漏说明、实际输出、耗时及真实调用用量。错误案例也保留。
- 公共仓库只提交有发布权的脱敏/合成资料；私有试点资料通过授权存储引用，不把客户原文和账号提交到 Git。

**B 验收**：关键字段能回到正确版本的原文；跨页/表格关系不会无声丢失；故意遗漏、损坏、超限和不能定位的内容均形成明确质量状态。mock 验证协议，真实视觉评测单列。

## 五、C / 李琦双任务（可立即开始）

### C1：真实需求→规则→用例的语义质量

- 基于 A 的试点样例补正常、边界、权限、多角色、状态变化和持久化检查；只覆盖资料明确支持或人工确认的预期。
- 缺业务条件、账号或准备能力时给出可处理的澄清/阻塞项；不得假定阈值、身份或数据已存在。
- 保持 APPROVED 入口限制、引用归属、冲突互指、覆盖对账与 UNPARSED 拒绝。不得降低已有约束来提高成功率。

### C2：计划建议稳定性

- 接管现有 `agents/planner.py` 的提示词与算法测试；当前版本为 `planner-v3`，升级由 A 同步调用方、契约和评测版本。
- 只引用 observation 中的目标；保持每个批准断言与检查动作对应。页面不足时明确阻塞。
- 保留“业务预期由 assert 判定”的约束，不恢复等待业务成功后才断言的做法，不靠重放写操作等到正确结果。
- 补登录准备、多角色切换、异步状态、元素消失、文本与金额断言样例。执行器变化交给 A，不在 Python 执行浏览器。

### C3：需求变更影响与评测

- 使用 B 的新旧来源比较，输出受影响规则/用例的建议及理由、引用；不得自行更新批准版本或缩小正式基线。
- 如果跨块/长资料暂不支持，仍明确超限或待复核；分块不能丢掉跨段冲突、条件与覆盖。本轮以试点需要决定是否实现分块。
- 相同健康版本、固定标准重复运行，建议每条关键旅程至少 3 次，保留首次失败和所有尝试；报告结构通过率、语义错误、阻塞原因、耗时、用量和人工介入，不用模型自评替代人工对照。

**C 验收**：真实生成资产通过 Python 与 TS 联合校验，并由 A 的真实浏览器执行；缺陷版本按冻结预期失败，修复版本无需放宽断言通过；不能只提交 mock 全绿作为算法完成证明。

## 六、共享接口与合并纪律

- A 维护：`packages/contracts`、Python `contracts/generated.py` / `schema.v1.json` / `validation.py`、`app.py` / `models.py` / `context.py` / `storage.py`、Prisma、公共依赖锁文件、TS/Python 联合反例。
- B/C 新能力先在自己目录完成纯模块和测试。需要改共享文件时给 A 一份最小字段/错误码/反例提案；A 负责统一落地。不能手改生成类型。
- B 输出来源与质量；C 消费来源形成建议；A 分配正式 ID、做二次校验、控制批准和执行。新旧输入都必须明确携带版本，不能用最新数据替换历史快照。
- 真实模型评测使用现有网关和独立测试开关，日常单测不默认访问付费模型。
- 每个 PR 写：改动目录、关联任务编号、实际测试命令与结果、真实/mock 区分、样例来源、仍未支持的范围。先模块验收，再联调。

建议合并顺序：A0 公共契约（仅必要变更）→ B1 解析质量 + C1/C2 可独立增量 → B2/C3 影响分析 → A 接线与 A2 运行器整链 → 联合验收。前端向导可与 B/C 并行，不能等所有算法完成才开始。

## 七、时间安排与完成定义

以下为计划估算，前提是试点项目、测试账号和可用模型配额到位，不是交付承诺：

- 第 0–1 天：A 确定试点、输入与接口；B/C 跑现有基线，建立各自评测夹具。
- 第 2–4 天：三条线并行；优先提交可独立合入的小增量。
- 第 5–7 天：第一个真实项目全链验收，修复阻塞；完成运行器整链及来源变化复核。
- 第 8–10 天：第二个业务项目、重复运行、干净环境启动、文档收尾。若外部项目缺失，明确延后试点门槛，不能以合成样例替代。

**本轮结束必须能展示**：原始资料来源 → 生成的规则/用例 → 人工确认记录 → 固定计划/构建 → 实际操作与证据 → 缺陷 → 修复复测；同时展示未验证范围、模型调用成本和人工介入记录。

本轮之后再排：受支持源码自动部署模板、更多测试框架/私有仓库、CI 自动触发、可组装 harness。新增功能以试点结果决定优先级。
