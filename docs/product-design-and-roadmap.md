# AI QA 产品设计与开发路线

版本：1.0｜日期：2026-09-18｜负责人：李博闻

## 1. 产品定位

面向多人协作和 AI 开发团队，依据已确认的业务要求，对集成构建进行独立测试，交付可追溯、可复现的验收结果。第一阶段替代重复回归、证据整理、缺陷复现和部分测试设计，逐步扩大自动化范围。

首批场景选择规则明确的 Web 后台：采购审批、订单、权限、状态流转。产品评价以真实缺陷检出和可复现性为核心，不以生成用例数量衡量效果。

## 2. 当前基线与差距

基线提交 c2a8287：真实浏览器固定用例闭环、多角色隔离、预算与取消、版本固定、证据校验、作业恢复已实现；Python 首版文档解析已实现。正式 Python 规则/用例生成、上传解析作业接线、完整审阅流程、生成步骤与页面绑定尚未完成。后续实现进度以 implementation-status.md 为准。

当前技术：TypeScript/Fastify 平台、PostgreSQL/Prisma、Redis/BullMQ、Playwright；Python/FastAPI 负责解析和智能算法。共享 Zod 定义导出 JSON Schema 与 Pydantic 类型。Python 不直接操作业务数据库和队列。

## 3. 用户与关键流程

- 测试负责人：登记环境与业务资料，确认规则，选择测试范围，审阅结论。
- 开发人员：读取缺陷证据，在对应构建上复现并修复，触发复测。
- 产品负责人：回答需求歧义，确认冲突条款和验收标准。

主流程：上传资料 → 解析与来源定位 → 提取规则草稿 → 澄清/审阅 → 批准规则 → 生成用例草稿 → 绑定页面/API 与数据准备 → 执行 → 缺陷报告 → 修复复测。

批准规则与可执行计划是不同资产。业务用例描述不能直接视为已绑定的执行计划；缺少账号、数据、定位或清理能力时明确阻塞。

## 4. 产品模块

### 4.1 资料与需求工作台

支持 Markdown/TXT/DOCX/PDF/图片上传、版本登记、SHA-256 核验和解析状态。保留来源页码/行号/单元格、无法解析的片段与覆盖统计。失败可以显式重试；需要 OCR 的文件不能直接进入规则提取。

展示规则原文、出处、显式/推断/未知分类和冲突关联。用户回答澄清时必须给出答案及来源，记录回答人与时间。尚未解决的问题阻止相关规则批准；语义修改通过新增规则版本完成，不覆盖冻结版本。

### 4.2 测试设计与资产管理

基于批准规则设计等价类、边界值、角色权限、状态转换、条件组合、重复与并发操作、失败恢复场景。保留需求→规则→用例→执行计划的引用。生成产物默认草稿，模拟模型产物明确标记，缺失信息不能由模型猜测填补。

### 4.3 执行与证据

浏览器、API、代码测试使用分离执行器，统一结果与证据接口。API 验证用于校验浏览器操作后的业务状态；必要时使用受控只读查询。环境、构建、数据、角色和测试版本共同固定运行身份。

结果区分业务失败、环境阻塞、证据不足和未执行。重试保留首次失败；定位修复不改变业务预期。报告能提供最小复现步骤、预期/实际结果和证据。

### 4.4 多人合并回归

PR/提交触发 → 核验部署构建 → 分析变更影响 → 核心冒烟 + 相关回归 → 发布结论。定期全量回归作为影响分析的兜底。需求变更使相关旧资产进入待复核状态。

### 4.5 代码正确性测试

逐步支持编译/类型/静态检查、既有测试执行、需求驱动的候选单元测试、属性测试、接口契约测试、集成测试和变异测试。预期来自确认过的业务规则，源码用于定位实现和选择测试范围，避免照抄错误实现生成错误测试。

代码测试在隔离副本及对应语言工具链中执行，不赋予生产资源访问权限，不自动改写业务代码。支持多语言不意味着重写各语言测试框架；通过执行器适配并收集标准报告。

### 4.6 Agent Harness

Harness 是模型、上下文、工具、流程、状态、权限、预算、校验与追踪的组合。产品优先提供业务验收、合并回归、探索测试三种模板，再开放配置化组合，最后建设可视化流程编辑器。

每个节点声明输入/输出契约、版本、资源权限、副作用、超时、重试与证据要求。用户可替换模型或增加工具；运行必须保留版本固定、真实/模拟隔离、证据完整性与统一判定约束。探索发现先作为候选缺陷，成功复现后再进入正式报告。

状态恢复可评估 LangGraph 检查点；外层作业生命周期由平台统一管理，内部图状态不能另行覆盖业务作业终态。当前不引入第二套编排框架作为完成阶段二的前置条件。

## 5. 开发里程碑与验收门槛

| 阶段 | 交付 | 验收门槛 |
|---|---|---|
| M1 需求到执行闭环 | 上传解析、规则/澄清审阅、正式生成、绑定与数据准备 | 一个真实业务系统从资料到可复现结果完整走通；缺陷构建失败、健康构建通过、信息缺失明确阻塞 |
| M2 合并回归 | API 验证、构建核验、CI 触发、差异选测、缺陷去重复测、偶发失败管理 | 明确关联提交与部署；相关业务缺陷可复现；不因重试抹去真实失败 |
| M3 代码测试 | 隔离代码执行、现有测试接入、候选测试、属性与变异测试 | 找到浏览器测试未覆盖的模块缺陷；生成测试有独立业务依据 |
| M4 Harness 产品化 | 模板、节点注册、配置组合、审计与版本比较 | 两类以上项目可复用；更换模型和流程可用同一评测集比较 |
| M5 按需求扩展 | 扫描 OCR 深化、性能、安全、无障碍和更多终端 | 每项有真实客户场景、独立评价指标和稳定运行成本 |

采用验收门槛推进，不把未经验证的日期或“替代全部测试人员”当作交付承诺。

## 7. 质量与验收指标

建立独立、保留答案的缺陷评测集；智能体不可接触评测答案。指标至少包括缺陷报告精确率、已知缺陷检出率、干净构建误报率、重复运行稳定性、需求遗漏率、引用正确性、单次成本、耗时和人工介入量。按测试类型分别统计，避免用大量简单用例稀释严重缺陷漏检。

上线试点前先记录人工测试基线，比较相同范围内的时间与检出效果。正式验收需要同时记录构建、环境、规则、用例、计划、模型、提示词与工具版本。

## 8. 近期优先级

P0：完成 A 平台接线和 C 正式生成；完成业务用例到执行计划的绑定闭环。

P1：API 验证、可靠测试数据、构建身份核验、缺陷复测与 CI 接入。

P2：代码测试执行器、属性/变异测试、配置化 Harness。

P3：通用可视化拼装、工具市场和更多非功能测试。先积累真实项目中的重复需求再推广。
