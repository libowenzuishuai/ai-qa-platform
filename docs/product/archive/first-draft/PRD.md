# AI QA 平台 1.0 产品需求文档

版本：1.0 设计稿｜日期：2026-09-20｜产品负责人：李博闻｜实现基线：`8491c4c`

> 本文是目标版本规格，不是完工声明。实现差距见 §3；交互原型中的项目、执行和报告全部为示例。1.0 定位为可用于受支持项目的团队试点版。

## 1. 产品定位与目标

为多人协作及 AI 辅助开发的团队提供独立测试：接入项目、依据确认的业务要求设计用例、在指定版本执行、输出能复现的问题与未验证范围。首批用户是开发 3–10 人、缺少专职测试或回归负担较重的团队。优先支持采购审批、订单、权限与状态流转类 Web 管理后台。

**一句话价值**：把“合并完代码后，谁来验收”变成有依据、有执行记录、有缺陷证据的工作流程。

### 1.1 1.0 成功定义

- 用户可以接入一个受支持的 GitHub 项目或已有测试网址。
- 仅提供源码时，可以完成项目健康检查；补齐业务资料、角色及数据条件后，可以完成选定业务基线验收。
- 从业务规则到用例、执行、证据和复测均有版本引用。
- 失败可区分项目缺陷、环境问题、信息不足和平台故障；不能用“执行完成”代替“验收通过”。

### 1.2 两种测试模式

| 模式 | 必要输入 | 输出 | 不得声称 |
|---|---|---|---|
| 项目健康检查 | 仓库版本、运行配置；或已有网址与授权范围 | 构建/已有测试/启动/选定页面冒烟结果、日志与截图 | 已满足全部业务要求；已有测试的预期必然正确 |
| 业务验收 | 上述环境 + 业务资料/已确认规则 + 角色账号 + 数据准备与清理方式 | 规则覆盖、断言、缺陷候选、证据、未验证范围、复测关联 | 从代码推导出的行为就是正确要求；无证据的业务通过 |

模式一不依赖 C 的用例生成完成即可开发；模式二是产品核心闭环。二者共享环境、版本、执行记录与证据能力，但分别展示结论。

## 2. 用户、权限与术语

| 平台角色 | 能做什么 |
|---|---|
| 管理员 ADMIN | 管理用户/项目访问、模型、仓库/依赖域名、隔离执行配置、密钥引用与保留策略 |
| 测试负责人 LEAD | 接入项目、上传资料、处理澄清、批准规则/用例、配置运行、启动/取消/复测、确认缺陷 |
| 查看者 VIEWER | 查看授权项目、脱敏报告与允许访问的证据；不能启动、批准或修改配置 |

平台角色不等于被测项目中的“申请人/主管”等业务角色。密钥不可通过普通读取接口回显，原始 trace 单独授权。

- **业务规则**：来自文档或有记录的产品确认，描述系统应该如何工作。
- **业务用例**：角色、前置条件、步骤、数据、预期和清理方式。
- **执行计划**：已绑定现场页面/API 目标、允许执行的结构化动作与断言。
- **基线**：本次选择的已批准规则、用例及计划版本集合。
- **构建**：特定源码提交产生的可执行产物；分支名或用户声明的版本号不等于核验过的构建。

## 4. 版本范围

### 4.1 1.0 必须交付

1. 两种接入：已有测试网址、GitHub 公共仓库。
2. 仓库模式先支持 Node.js 22、npm/pnpm 锁文件、单个 Web 服务；可选平台提供的独立 PostgreSQL 测试实例。子目录由用户指定，不能承诺自动部署任意 monorepo。
3. 安装、构建、已有测试、启动、健康检查，提供准备失败原因及日志。
4. Markdown/TXT/DOCX/PDF/PNG/JPEG 资料，规则与澄清，已批准规则生成用例。
5. 用例编辑批准、页面观察绑定、角色与数据准备、冻结本轮范围。
6. Chromium 的受限浏览器执行、持久化验证、多角色顺序协作、证据、取消与恢复。
7. 独立展示健康结论与业务验收结论，最小缺陷确认、关联新运行复测，Markdown/JSON 导出。
8. 真实/模拟隔离、项目权限、构建/资产版本固定、资源预算和审计。

### 4.2 1.1 / 后续

私有仓库 OAuth/GitHub App、多语言自动运行、多服务 compose、PR 自动回归、增量选测、API 专用执行器、并发业务测试、自动重试与 flaky 管理、精细文字框/复杂表格、属性/变异测试、配置化 Harness。

任意 shell 自由生成执行、自动修复并提交被测代码、移动端、生产操作、安全攻防、压测、多组织计费、通用可视化智能体编排不属于 1.0。此前 0.1 PRD 中列为 P0 的 Midscene、下载/API 检查及自动额外 attempt，本版明确后移；不能把尚未支持的能力当作业务断言已执行。

全局：项目列表 / 新建接入。项目内：概览、需求资料、规则审阅、测试用例、环境与绑定、测试运行、缺陷报告、项目设置。

| 原型页面 | 核心操作 | 页面出口 |

| 接入向导 `#connect` | 选 Git/网址、填写来源、核对配置、准备预览 | 保存配置、进入环境或健康检查 |

## 6. 核心用户旅程

### A. 只有仓库地址

输入地址 → 选分支/提交/子目录 → 读取项目描述生成配置草稿 → 用户确认命令、端口及所需变量 → 固定完整 SHA → 隔离安装/构建/已有测试 → 启动就绪 → 首页/选定页面冒烟 → 健康报告。

没有测试脚本：已有测试显示“未提供”，覆盖不足；没有启动条件：环境阻塞。两者都不能包装成全部通过。

### B. 根据业务资料验收

已接入环境 → 上传 PRD/原型 → 检查解析遗漏 → 提取规则草稿 → 处理冲突/缺口 → 批准规则 → 生成用例 → 编辑/批准 → 验证角色和数据 → 观察并绑定 → 冻结基线与构建 → 运行 → 查看失败断言 → 确认缺陷 → 在新构建复测。

允许对清晰、已批准的部分建立范围明确的基线，不要求所有文档问题都解决才能做任何测试；报告必须保留未覆盖范围。

### C. 已有测试网址

登记非生产环境与允许域名 → 核对授权范围 → 验证连通/角色/数据 → 登记构建；无法核验构建时允许调试执行但业务正式验收保持 INCOMPLETE → 复用旅程 B。

## 7. 功能需求与验收标准

### FR-01 项目接入与来源版本（P0）

- Git 表单：项目名、HTTPS GitHub 公共仓库、分支/标签/提交、可选子目录、测试模式。只接受支持的 URL 形状，禁止本地路径、凭据嵌入、任意 URL 协议；后端重复校验。
- Clone 在独立目录使用结构化参数，禁交互凭据提示，不递归子模块，不默认下载 LFS；需要这些能力时显示不支持。
- 解析并保存完整 SHA；后续分支移动不会更改已经创建的构建。
- 版本引用、配置版本和依赖锁文件指纹可查看；同项目同请求幂等去重。
- 已有网址表单：环境名、baseUrl、允许域名、构建声明与核验方式，生产环境拒绝。
- 验收：同名分支发生新提交后，已排队任务仍执行旧 SHA；错误仓库、找不到 ref、越界子目录有字段级提示。

### FR-02 配置发现与确认（P0）

- 读取 package.json、锁文件及声明端口，提供配置草稿；README/仓库文字属于待分析数据，不能授权工具或覆盖系统规则。
- 显示 Node 版本、包管理器、工作目录、安装/构建/测试/启动命令、端口、就绪路径、依赖实例及所需环境变量名称。
- 命令建议必须确认后形成配置版本；不把 LLM 猜测的启动方式自动视为可执行事实。修改配置产生新版本。
- 未配置测试脚本显示“未提供”；不自行伪造测试数量。缺锁文件/不支持的工具链标记需补充条件。
- 验收：含恶意指令的 README 不改变权限；保存时校验必填和端口；缺少环境变量阻止启动并只显示变量名。

### FR-03 隔离构建与环境（P0）

- 项目源码及 npm 生命周期脚本均是不可信代码。独立执行器与平台 API/worker 分离；执行环境无平台密钥、宿主目录、Docker socket或生产资源访问权。
- 环境按项目/构建独立分配；只有所需临时测试凭据被注入。依赖下载阶段的出口与业务测试阶段出口分开控制。
- 资源/进程/磁盘/网络有上限；取消终止对应进程树，超时释放环境，清理失败留可追踪状态并由对账回收。
- 默认建议：准备 10 分钟、已有测试 5 分钟、2 vCPU/2 GiB/2 GiB 临时磁盘；管理员可在策略范围内修改。这是目标配置，不代表已做容量验证。
- 构建、启动失败属于对应检查失败/环境阻塞，不自动记作业务 FAIL；保存退出码和脱敏日志。
- 验收：异常退出能收敛到终态；失联任务不会永久运行；连续两项目执行不共享数据或凭据。

### FR-04 构建身份与就绪（P0）

- 管理环境把源码 SHA、构建配置、产物 digest、启动实例关联；进入运行前核验实际实例并记录运行期间漂移。
- 源码 SHA 不单独构成 buildVerified=true。已有网址需可信部署清单/版本端点与环境实例核对，只有用户填写版本号时显示“已声明，未验证”。
- 就绪检查验证端口/路径；账号检查验证对应角色登录；两者不等于业务验收通过。
- 验收：测试中替换实例或版本发生漂移，正式验收 INCOMPLETE；同一报告展示声明版本与核验结果。

### FR-05 资料与解析（P0）

- 复用现有 20 MB 文件、版本及来源契约。PDF 先整页渲染，再调用视觉模型；现有预算每份最多 20 页模型请求/120 秒，超过预算有页级遗漏。
- 每份资料展示原始文件、校验和、解析版本、来源片段、LOW/UNPARSED 和警告。PARSED 表示有可用正文，不表示全部理解。
- 不完整片段进入待处理范围，不能让空内容伪装成规则；PDF_SCANNED 可以是 PARSED。
- 验收：点击规则出处能打开确切文档版本和片段；重新上传不覆盖已引用原文；错误文件可重试。

### FR-06 规则审阅与澄清（P0）

- 规则区分 EXPLICIT/INFERRED/UNKNOWN，模型输出默认草稿。
- 冲突双方和来源都保留；缺失条件生成问题，不补造阈值或角色。回答必须带来源、回答人、时间。
- 未解决的关联澄清阻止批准。已批准规则的语义修改产生新版本、触发相关用例复核，不覆盖冻结版本。
- 批量批准只接受没有未解决问题的规则；部分失败逐项说明，不伪造整批成功。
- 验收：资料只定义“>5000 需要审批”时，未定义的 <=5000 行为保持未知；解决冲突后仅明确选择的版本可批准。

### FR-07 用例与覆盖（P0）

- 只从 APPROVED 规则生成；每用例保留规则版本、角色、前置条件、步骤、断言、数据与清理，编辑产生新版本。
- coverageMap 与 blockedRequirements 对账；缺能力/账号/数据明确阻塞，不补造 selector、业务字段或测试预期。
- 用例批准和可执行状态分别展示；已批准但未绑定/缺条件的用例不能显示“可运行”。
- 模型/未知来源的 mock 产物不得用于 real 验收；人工资产有明确来源及审批记录。
- 验收：边界按已确认规则使用 499999、500000、500001 分等具体数据；没有定义的边界不能编造预期。

### FR-08 页面绑定、角色与数据（P0）

- 复用 TestPlan v1：动作只能引用登记的 targetRef；观察绑定含 URL、时间与证据，不能凭空产生 selector。
- 首版支持模型辅助观察和人工修正；定位歧义需选择/重新观察；计划 schema 校验、引用闭合、非空必需断言和 acceptanceHash 核验后发布。
- 每角色独立会话，凭据通过密钥引用；缺账号/过期/验证码按原因阻塞。
- 数据模板由负责人预先登记，按命名空间准备和清理；模型不得任意生成 SQL/shell 数据操作。
- 验收：绑定变化不能修改 operator/expected/required；没有观察证据不能发布计划；两次运行数据隔离。

### FR-09 启动与执行（P0）

- 选模式、环境、构建、基线/用例和预算，启动前展示就绪检查、待处理项与具体范围；未就绪项目不得被忽略。
- 冻结规则/用例/计划/环境配置/模型提示词版本；排队后变化不改写本轮资产。
- 复用现有生命周期、租约、幂等、SSE 与取消逻辑。步骤与必需断言分开记录。
- 1.0 不承诺自动额外 attempt；失败复测是明确关联的新运行。任何后续重试都必须保留首次结果，不能抹除失败。
- 验收：完成页面点击但断言未执行的用例不能 PASS；账号失效应 BLOCKED；取消后未执行用例保留 NOT_RUN。

### FR-10 报告与判定（P0）

- 健康检查分别展示构建、已有测试、启动、页面冒烟；没有执行的检查为 NOT_RUN/不可用，不以退出码之外的猜测判定。
- 业务用例状态沿用 PASS/FAIL/BLOCKED/REVIEW/NOT_RUN；运行 lifecycle 与 acceptanceStatus 分离。平台 ERROR 不等于业务 FAIL。
- 严格验收：可信业务 FAIL 优先为 FAIL；无 FAIL 但有阻塞/待复核/未执行/证据缺失/构建未核验或漂移则 INCOMPLETE；非空冻结范围完整满足才 PASS。
- 分母：通过比例=PASS/选定用例数；执行率=(PASS+FAIL)/选定用例数；零分母为 N/A。规则覆盖率单独展示，不能等同资料完整率。
- 证据含 expected/actual、版本、角色、业务数据 ID、截图/trace及来源；文件缺失、归属不符或校验和变化降级，不产生无证据通过。
- 验收样例：4 个选定用例，2 PASS、1 FAIL、1 BLOCKED → 总体 FAIL，通过比例 50%、执行率 75%；非“75%通过”。

### FR-11 缺陷与复测（P0）

- 候选缺陷由规则来源 + 违反断言 + 证据构成；模型猜测只作为待复核说明。
- 最小流程：待确认 → 已确认 → 待复测 → 已验证/重新打开；映射沿用现有缺陷契约，不擅自替换枚举。
- 按规则/断言/错误签名聚合，同一缺陷在不同构建保存独立 occurrence。
- 复测创建新运行，展示旧/新构建、同一基线及变化；通过后负责人确认关闭，旧失败不可被覆盖。
- 验收：证据不可见时解释权限或缺失；新版本通过不能自动删除旧报告。

### FR-12 配置、权限和使用量（P0）

- real/mock 常驻可见；原型使用“交互原型·示例数据”，不冒充真实执行。
- 文本与视觉模型单独配置；记录 provider/model/提示词版本/实际 token。价格未登记时金额显示未知，不给虚构估价。
- 预算到期停止新调用/动作；真实配置缺失明确报错，禁止自动降级 mock。
- 服务端权限覆盖项目资产、日志、执行控制、原始证据。用户输入需转义；报告隐藏密钥与敏感请求头，原始附件采用受限权限和保留策略。
- 验收：VIEWER 直接请求写接口仍被拒绝；跨项目文件不可下载；配置只返回是否已设置。

## 8. 数据与接口边界（设计，不表示已实施迁移）

保留：DocumentVersion/SourceSpan/RuleVersion/TestCaseVersion/TestPlanVersion/Baseline/Run/Attempt/Artifact/ModelInvocation 等现有资产。

拟新增/完善：

| 资产 | 最小字段 | 约束 |
|---|---|---|
| RepositoryConnection | projectId、provider、canonicalUrl、默认 ref | 1.0 只接受公共 GitHub HTTPS，不保存 URL 内凭据 |
| RepositorySnapshot | repoId、requestedRef、resolvedSha、subdirectory、lockfileHash | SHA 解析后冻结 |
| ExecutionProfileVersion | runtime、commands、port、readiness、secretRefs、resourceLimits | 修改生成版本，确认与审批留痕 |
| BuildArtifact | snapshotId、profileVersionId、digest、日志引用、结果 | 构建失败不伪造 digest |
| ManagedEnvironment | buildArtifactId、实例身份、endpoint、过期时间、清理状态 | 与平台数据和其他项目隔离 |

仓库准备是独立作业，不扩展 Run.lifecycle 为 BUILDING 等混合状态。新作业类型、取消和错误码先通过公共 Zod 契约评审，再导出两端类型。候选 API 分组 `/repository-connections`、`/repository-preparations`、`/execution-profiles`、`/managed-environments` 仅作为设计；实现前核对现有路由和幂等契约。

业务运行必须引用已准备环境、实际构建及资产版本；浏览器执行器不负责 clone/build。Python 继续负责文档和智能分析，TypeScript 平台负责鉴权/作业/持久化，隔离执行器运行被测项目工具链。

## 9. 原型交互与设计规范

- 布局：固定项目导航、内容工作区、右侧证据/来源侧栏；主要动作每页一个清晰入口。
- 风格：浅色内容、深色导航；蓝色动作，绿/红/橙表达通过/失败/阻塞，同时配文字，不能只靠颜色。
- 每个阻塞信息包含原因及可执行的下一步；不能只给内部错误码。
- 原型覆盖：接入三步、资料选择、澄清保存后批准、用例草稿审批、环境准备、模拟执行与取消、失败证据、复测关联、导出示例报告。
- 所有表单可通过键盘操作，有标签与焦点样式；侧栏/弹层支持 Esc；窄屏允许导航折行和表格区域滚动。
- 原型不会拉仓库、上传文件、执行命令、调用模型或发送凭据；本页刷新恢复样例数据。文件选择仅演示名称和大小。

## 11. 1.0 发布验收与质量指标

以下是目标门槛，不能当作已取得的数据：

1. 两个独立 Node.js Web 项目，其中至少一个含平台提供的 PostgreSQL；另验证已有网址入口。
2. 一条完整双角色业务路径：资料 → 规则 → 澄清批准 → 用例 → 绑定 → 真实运行 → 证据 → 新版本复测。
3. 维护独立隐藏答案的评测集，覆盖健康构建、业务阈值错误、越权、状态不一致与持久化缺陷；智能体不可读取答案。
4. 发布评测中预置关键缺陷全部检出，健康样例不出现误报；按项目和缺陷类型公布样本数、检出率/误报数，不能推广成任意项目保证。
5. 任一 PASS 都具备实际必需断言与完整证据；空范围为 N/A；缺构建核验不能正式 PASS。
6. 分支移动、重复投递、取消、失联、缺配置、超限、证据篡改、跨项目访问都有独立反例。
7. 展示运行耗时、实际 token、人工介入次数、需求遗漏范围和准备失败原因；真实模型评测与 mock 测试分别统计。
8. 同一基线至少重复 3 次记录稳定性，首轮失败不能因后续通过消失；仍不等于生产规模负载验证。
