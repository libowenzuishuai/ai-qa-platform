# AI QA 1.0 · 软件验收平台 PRD

2026-09-20 · 产品重设计稿 r2 · 实现基线 `8491c4c` · 负责人：李博闻

> 本文定义目标产品。当前代码仅实现其中部分基础能力；原型全部是本地示例。战略与商业假设见 [产品战略](../../v1.0/PRODUCT-STRATEGY.md)，原型见 [交互说明](../../v1.0/prototype/README.md)。本稿取代本日初稿的产品导航、接入方式和版本范围；初稿已归档。

## 1. 定位

**接入软件项目，说明测试目标，获得有依据、可复现的交付结论。**

产品面向高频交付和 AI 辅助开发的团队。核心对象是项目及其每一次变更，不绑定采购、订单或任何单一业务。长期承担测试设计、执行、缺陷复现与回归工作；1.0 首先完成 Web/API 软件交付验收的可信闭环。

用户要回答：这次改动哪些已验证、哪些出问题、哪些仍未知、下一步谁处理。页面以这些问题组织，隐藏不必要的内部任务类型、状态机和 ID；工程细节可以展开，但不强迫每个人先配置全部底层节点。

### 1.1 通用性的定义

- 通用输入：源码仓库、运行网址、接口契约、资料、既有测试、用户确认。
- 通用项目结构：服务、环境、业务能力、角色、需求依据、测试资产及变更，不写死行业表结构。
- 通用执行协议：浏览器、HTTP API、既有测试分别产生标准结果和证据；模型可以更换，执行器可以适配。
- 通用交付结论：不同技术栈共享依据、版本、范围、证据和未验证项。
- 通用不等于自动运行所有仓库、理解所有资料，或把未来能力标为已支持。兼容范围和缺口必须可见。

## 2. 目标用户与场景

首批试点：已有测试环境、频繁发布的 5–30 人 SaaS / AI 应用团队。覆盖至少两种业务类型，避免只在自建 demo 上成立。技术负责人/QA 负责人购买与配置，开发与产品人员协作确认，查看者消费报告。

| 场景 | 用户目标 | 必要前提 | 输出 |
|---|---|---|---|
| 发布验收 | 本次版本能否按选定标准交付 | 确认的基线、实际运行构建、账号/数据 | 有证据的通过/失败/未完成，决策待办 |
| 变更回归 | 改动是否破坏既有功能 | 新旧提交/版本、已有基线；缺变更清单时全范围 | 影响建议、选定回归、明确未测范围 |
| 项目体检 | 快速了解能否构建/启动、有何明显异常 | 仓库或网址、授权范围 | 工程健康与候选问题，不等于业务验收 |
| 缺陷复测 | 修复是否生效、是否引入回归 | 旧缺陷、可复用预期、新构建 | 新运行与旧失败关联，负责人确认关闭 |

自动复杂影响选测不是 1.0 强依赖；用户指定范围 + 核心冒烟即可启动。探索发现若无确认过的业务依据，标记候选，不伪装成需求违规。

## 3. 从旧设计到新设计

| 旧路径 | 新路径 |
|---|---|
| 接入仓库后再手动上传仓库内 PRD | 一次接入，发现并分类仓库资料，用户仅补充或确认 |
| 固定示例项目的功能菜单 | 团队多项目工作台 + 项目内上下文与任务 |
| 先填多个技术表单才能看到价值 | 先给目标与入口，系统列发现、建议与缺口，技术配置渐进展开 |
| 围绕文档/规则/用例表逐步操作 | 围绕任务推进，资产可追溯，待决问题集中处理 |
| 测试数、通过率主导首页 | 当前交付风险、待处理决策、任务结果与未覆盖范围 |
| 把 AI 生成当作核心差异 | 关注测试依据独立性、结果复现和连续复测 |

## 4. 产品信息架构

一级导航：**工作台 / 项目空间 / 产品上下文 / 测试任务 / 执行中心 / 交付评估 / 能力与集成**。

- 工作台：团队视角的任务入口、项目概况、需要人处理的决策、最近交付。
- 项目空间：统一接入、服务/环境/版本、连接状态；一个项目关联多个资料来源与运行目标。
- 产品上下文：资料来源、业务规则、未决问题、变更影响；原“需求资料”和“规则审阅”成为相邻视图，不再重复输入。
- 测试任务：用户目标、推荐范围、依据、预计工作量/预算、执行条件、任务模板；用例在范围内查看与编辑。
- 执行中心：准备、执行、证据、清理、人工接管与失败恢复。
- 交付评估：结论优先，风险/证据/覆盖缺口/复测和导出。
- 能力与集成：连接器、运行器、测试能力、模型与治理；显示当前代码/1.0 目标/后续规划三类状态。

1.0 仍有必要的设置和登录，但不把设置当作产品第一屏。原型旧路由 `#runs` 等重定向到新导航，保持已有链接可用。

## 5. 核心旅程

### 5.1 一次接入，建立项目上下文

1. 粘贴 GitHub 地址或测试网址；也可声明使用自有运行器。
2. 只读发现：固定提交 → 识别服务/配置/已有测试 → 查找业务资料与接口契约。
3. 展示“发现了什么”和“仍缺什么”。Git 已包含 PRD 时自动列入候选，不要求再上传。
4. 按资料用途确认纳入和依据等级；存在冲突时形成待决事项。
5. 运行条件不足时可先分析资料，不能假装已有可运行环境。
6. 建立上下文快照，生成首个测试方案。

### 5.2 目标驱动的测试任务

“验收本次订阅升级和退款变更，重点检查权限与重复提交。”

系统提出：目标环境/构建、资料快照、必测用户旅程、测试方式、可复用用例、阻塞项、预算。用户在关键节点确认后冻结任务；执行器按固定计划运行，发现缺口进入待办。已确认基线的重复回归不重复要求批准每条规则。

### 5.3 交付评估与复测

先展示关键失败和未验证范围，再展开用例数量。点失败可看到要求原文 → 冻结规则 → 步骤与断言 → 实际结果 → 证据 → 复现路径。新构建复测保留旧记录，不能通过放宽断言获得“修复”。

平台给验收结论与建议；是否发布由有权负责人决定。人工接受风险记录在交付决策中，不把失败的测试改成 PASS。

## 6. 项目上下文：资料自动发现与可信边界

### FR-CTX-01 仓库发现

- 输入：规范化 HTTPS GitHub 地址、ref、可选子目录。解析完整 SHA 并冻结，后续分支变化不改写任务。
- 扫描 README、docs、PRD/requirements/spec 相关文件、OpenAPI、包/测试配置；通过路径/格式初筛和模型分类，不仅靠文件名。
- 记录 repo+commit+path+blobHash，版本来源不可变；识别到相同文件时复用快照引用，不重复上传。
- 文件数量、累计字节、单文件、路径范围有预算；不跟随越界链接/子模块，不读取 .env、私钥等凭据文件。跳过条目和达到上限原因可见。
- 扫描仅产生候选分类；README 内指令、源码注释、图片文字不能改变平台权限或调用策略。
- 无资料时仍可做工程健康/探索，业务依据明确不足，不自动从实现编造需求。

### FR-CTX-02 来源分级

| 内容 | 默认用途 | 可否直接批准为业务预期 |
|---|---|---|
| 版本化 PRD/业务说明 | 候选业务依据 | 需按项目批准策略确认；冲突先解决 |
| 产品人员补充说明 | 人工确认依据 | 记录作者、时间与来源后可批准 |
| OpenAPI/契约 | 接口结构/协议依据 | 结构约束可用；业务含义不能超出文档 |
| README/部署说明 | 运行配置及项目概况 | 不默认是业务权威，有明确条款时可挑选 |
| 源码/既有测试 | 实现线索、范围与复现辅助 | 不能单独证明业务应如此 |
| 模型推断 | 待确认假设 | 不可自动变成 EXPLICIT/批准要求 |

跨文档冲突不能自动用“最新文件”解决。用户选择优先来源或补充决定后留下审计记录；被否决依据仍可查看。

### FR-CTX-03 持续更新

新提交资料变化生成新上下文快照，显示新增/修改/删除来源及受影响规则。旧任务保持原快照；受影响资产待复核。避免全量重生成所有用例。1.0 可手动同步，自动 webhook 后移。

解析沿用现有格式/质量/遗漏约束。PDF 20 页视觉请求/120 秒为当前上限，不将 PARSED 当作无遗漏。每一处无法识别应带定位，扫描格式也可以包含已识别正文。

## 7. 任务与验收策略

### FR-TASK-01 任务简报

字段：项目、用户目标、模板、目标版本、环境、上下文快照、范围/排除项、验收依据、预算、负责人。缺字段时给最少必要问题，不重复询问已有上下文。

建议计划必须说明测试维度、每个用例依据、执行能力及准备条件；界面先展示业务旅程，技术动作可展开。模型自报置信度不能代替验收。

### FR-TASK-02 冻结与审批

- 自动执行的只读发现、建议生成，与有副作用执行分开。
- 首次业务规则/数据副作用/写操作范围需要负责人确认；预算扩大、目标域名变化和核心预期变化需要重新批准。
- 冻结后保存规则/用例/计划/资料/环境/模型/提示词版本及 acceptanceHash。
- 草稿与批准、批准与可执行分别展示；不能把缺绑定、角色或数据的项目显示成可执行。
- 计划排除必测能力时列出未验证范围，完整交付结论不得 PASS。人工缩小正式基线需要说明和审计，不能由 agent 自行降低门槛。

### FR-TASK-03 测试资产

复用既有 RuleVersion/TestCaseVersion/TestPlan，不重新发明第二套资产。用户可从任务下钻到用例编辑批准与页面绑定。核心数值/权限/持久化由确定性断言验证；模型用于建议、解释和受约束探索。

缺角色、夹具、超长资料、schema 不合格、引用错误、覆盖遗漏都明确处理。规则模型输出要通过 Python 公共校验和 TS 落库二验。

## 8. 通用执行能力与 1.0 边界

### FR-RUNNER-01 能力矩阵

| 能力 | 当前实现（2026-09-20） | 1.0 发布目标 | 后续 |
|---|---|---|---|
| 已部署 Web / Chromium | 通用观察/计划批准已接通；两类合成业务验证 | 通用观察绑定、业务路径与多角色顺序执行 | 多浏览器/原生移动 |
| HTTP API | 注册模板、标量断言与证据已接通 | 登记接口/认证、结构及业务断言、幂等/权限检查 | 性能/安全专项 |
| Node.js 已有测试 | 内置 test runner 隔离执行已验证；真实仓库整链待验 | 受控命令、锁文件工具链和结构化报告导入 | 更多构建类型 |
| Python 已有测试 | pytest/JUnit 隔离执行已验证；真实仓库整链待验 | 经用户配置的隔离运行器导入 pytest/JUnit 结果 | 自动多语言环境发现 |
| 自有执行器 | 认证/领取/租约/结果协议已有；模块分别验证 | 认证协议、领取任务/提交结果、证据归属与租约 | 更多语言与工具适配 |
| AI 应用 / agent 质量 | 未实现 | 不纳入正式 1.0 通过能力 | 数据集、轨迹、工具使用与业务评测 |
| Harness 组装 | 未实现 | 固定的可配置任务模板与节点协议 | 可视化组装、插件生态 |

表中 1.0 是开发门槛，不是已支持声明。自有运行器能接入更多技术栈，但用户仍需提供环境/命令/结果适配；不能承诺只给地址就全自动运行任意项目。

### FR-RUNNER-02 运行部署路径

- 已有网址：最快起步路径，语言无关，但需要账号、数据、网络授权及构建核验。
- 托管运行器：先内建单服务 Node.js + 可选独立 PostgreSQL 模板；自动构建明确受支持的仓库。
- 自有运行器：部署在客户测试网络，以最小权限取任务；1.0 验证一种 Python 既有测试接入。多服务启动由客户现有 CI/环境承担。
- 源码和依赖安装脚本视为不可信执行，隔离于平台进程/数据库/密钥，无宿主挂载和 Docker socket，按阶段限制网络出口。
- 新运行器调用同一租约、幂等、版本、证据协议；提交结果不能自报越权项目或在取消后覆盖终态。

### FR-RUNNER-03 操作与失败

复用 Run 生命周期/Case verdict。准备作业不混入业务断言结果；支持准备/执行/清理分别观察、取消、超时、失联对账。

多角色隔离；数据按命名空间清理；副作用不明时不盲目重放提交。1.0 以显式复测为主，不把自动重试当强制能力。失败恢复不能修改验收预期。

构建验证必须关联实际产物/实例，SHA 或用户填的版本只是声明。证据缺失、篡改、归属错误不能通过；原始 trace 单独授权。

## 9. 交付评估与结果合同

### FR-RESULT-01 判定

- 业务用例：PASS / FAIL / BLOCKED / REVIEW / NOT_RUN。
- 严格验收：可信 FAIL 优先；无 FAIL 但存在阻塞/待复核/未执行/构建未核验或漂移/必要证据缺失为 INCOMPLETE；非空已批准范围全部满足才 PASS。
- 工程健康、业务验收、探索候选分别展示，不用一个混合“质量分”掩盖不同证据等级。
- 平台 ERROR 与业务 FAIL 区分；报告清楚显示当前任务及数据的 real/mock 来源。
- 展示原始计数与分母。通过比例 PASS/选定数；执行率 (PASS+FAIL)/选定数；零分母 N/A；资料覆盖与代码覆盖另算。

原型默认：22 个选定检查，19 PASS、1 FAIL、1 BLOCKED、1 NOT_RUN；通过比例 86.4%，执行率 90.9%，总体 FAIL。范围变化后重新计算，但排除必测项仍保留缺口。

### FR-RESULT-02 缺陷与复测

失败卡片：用户影响、严重度依据、要求出处、复现、expected/actual、实际证据、版本、处理人。疑似根因与已验证事实分开。相同缺陷跨版本 occurrence 保留，可关联新任务复测并比较，不自动覆盖旧结果。

发布决定单独记录负责人和理由。接受风险不改写测试结果；不能自动代替负责人发布软件。报告可导出标准 JSON/Markdown，链接受项目访问控制。

## 10. 产品级治理

- 项目权限和租户/工作空间隔离由服务端实施；原型不是权限实现。跨工作空间 SaaS 属商业部署阶段需补的能力，不以现有项目鉴权冒充。
- ADMIN/LEAD/VIEWER 保留；审批和受限证据下载有审计。
- 模型可替换；文本/视觉能力分开配置，真实模式缺密钥直接失败。记录实际 token；未知价格不虚构金额。
- 每任务预算分模型、浏览器、构建等；预算提高需要确认，在途调用可能有费用尾差。
- 客户源码默认不用于跨客户训练；数据保留、删除、导出与私有运行器契约明确。
- 公共源码初次导入只做白名单只读发现；私有仓库在 1.0 试点用客户网络内的运行器/受控导出接入。OAuth 托管连接器必须实现凭据域和撤销后才能宣称支持。

## 11. 领域模型与架构方向（待实现规格）

保留现有资产和 Run/Attempt/Artifact 协议。新增项目层描述与任务层编排：

`Project → Connections → ContextSnapshot → Mission → PlanSnapshot → Runs → Findings → Assessment`

- Connection：来源类型、授权域、同步版本，不直接包含明文凭据。
- ContextSnapshot：不可变来源引用、用途/依据等级、质量/遗漏、项目确认记录。
- Mission：用户目标、模板、范围、预算、负责人；可以关联多个已有 Run，不替换它们的状态机。
- PlanSnapshot：规则/用例/运行器绑定、必测与排除项、执行条件及版本。
- RunnerCapability：支持类型/版本、限制、权限、输入输出 schema。
- Assessment：基于冻结范围及可核验证据的汇总，发布决定是独立记录。

TypeScript 平台承担身份/作业/资产/审计；Python 智能服务承担资料分类、规则分析、用例/计划建议与解释；隔离运行器承担实际项目命令/浏览器/API 执行。所有新增字段先改 Zod，再导出 Schema/Pydantic，不能在三端独立手写不一致契约。

Harness 首先是版本化流程节点：发现→分析→规划→准备→执行→核验→报告；每节点有工具权限、预算、恢复和输出校验。1.0 提供模板配置，后续视觉编辑器也不能绕过证据与验收规则。

## 12. 交付路线与验收

## 13. 发布验收与度量

- 至少两个业务类型的项目；已有网址路径和受支持的仓库路径各完成一次从接入到报告，至少一次新构建复测。
- 一份仓库 PRD 无需手动再上传；自动发现正确记录 commit/path/hash。变更产生新快照，旧运行不漂移。
- 无资料、资料冲突、低质量、超长、账号缺失、构建不匹配、未知副作用都形成可处理状态。
- 关键隐藏缺陷与健康对照集分开；报告准确性、检出率、复现率、样本数、重复稳定性、人工分钟和成本分别记录。
- 核心结论不由模型自由文字决定；不可空范围 PASS；不得只用覆盖率或运行成功率证明业务正确。
- 来源/上下文一旦批准，不允许静默改写；取消不能留下无限运行任务；证据必须真实存在且归属正确。
- 商业试点另记录团队周留存、报告采纳、到首个可信结果时间；本稿不虚构 ROI 或质量承诺。

## 14. 原型规范与当前交付

新版原型采用团队工作台、统一接入发现、上下文证据链、目标驱动任务、并列执行能力、结论优先报告。以中性 SaaS 示例展示，同时展示其他项目类型，业务不是固定采购审批。

所有发现、生成、运行、图表和证据均标明本地示例。交互只改变内存状态，不克隆仓库、调用模型、上传文件、创建真实任务或发布项目。原型展示的 API/代码执行等为设计目标；能力页标出当前实现与规划。

原 0.1 文档作为契约背景，r1 设计在 `docs/product/archive/first-draft`；本稿是当前产品方向。尚未变更的生产代码以实施状态和提交验收为准。
