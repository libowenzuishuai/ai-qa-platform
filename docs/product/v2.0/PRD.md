## 0. 执行摘要

用户期望的产品不是一组固定测试脚本，而是能够接受“验收本次交付”这个任务，理解资料、调查项目、选择工具、准备数据、探索业务、执行测试、提出缺陷并复测的 AI 测试人员。

2.0 以五个结果衡量：

1. **陌生项目可接入**：支持范围内的新项目，无需修改平台源码即可完成接入与第一条业务验收；不支持的部分能明确说明。
2. **执行过程可适应**：弹窗、异步加载、入口变化等操作问题可在批准范围内解决；业务断言保持不变。
3. **工具可真正组装**：新工具通过适配器协议加入，支持重复节点、子流程和有界循环；业务用户可以使用预设，技术用户可以扩展。
4. **缺陷可以复现**：报告包含标准、实际结果、最小复现和证据；疑似问题、执行故障和已确认缺陷分开。
5. **价值可测量**：公开相同条件下的检出、误报、人工时间与费用数据，而不是以代码行数、用例数或平台单测数量代替效果。

首发覆盖 **Web + HTTP API + Node/Python 工程测试**，同时设计可扩展执行协议。原生移动端、桌面、专项性能/安全扫描、任意技术栈自动部署属于后续适配，不以“通用”一词默认为已经支持。

## 1. 诚实基线：从哪里开始

| 方面 | 1.0 已有基础 | 2.0 必须新增的实质能力 |
|---|---|---|
| 资料 | 解析、来源、分块、多文件变更 | 按任务检索业务上下文、覆盖地图、冲突处置进入规划 |
| 测试设计 | 规则/用例/计划建议 + 人工批准 | 风险驱动策略、候选补充、数据驱动用例、可解释的范围对账 |
| 执行 | 固定 TestPlan 七动作与角色隔离 | 实时观察、有限重规划、DOM/视觉操作、复杂页面适应 |
| Harness | 11 个固定 handler、DAG、每类业务能力通常仅一次 | 注册式适配器、类型化绑定、重复节点、子流程、有界循环、回放 |
| 目标规划 | 目标 + 能力目录 + 有资料/环境标记 | 真实资料/规则/运行状态/记忆组成的上下文，不只传布尔值 |
| 探索 | 无脚本匿名静态 GET 观察 | 经授权的登录态交互探索，业务状态和覆盖驱动的下一步选择 |
| 记忆 | 带来源与 TTL 的记录 | 自动检索、实际使用记录、冲突/过期处理和效果反馈 |
| 诊断 | 原因码与证据归类 | 网络/日志/变化关联、竞争性根因假设、复现与反证 |
| 工程测试 | 已有测试/构建/LCOV，有限部署 | 从独立依据生成候选测试、有效性检查和缺陷/修复对照 |
| 模型 | Moonshot 正式通道、mock 评测 | 生成/视觉/决策独立协议与路由；提供商可替换，不串用协议 |
| 产品化 | 可运行页面、数据库、恢复与证据 | 首次接入引导、实时控制台、可用的组合设计器、效果仪表盘 |

当前 1.0 可以有人指导地试点；没有证明能通用替代 QA。975 项平台检查不是业务检出率。2.0 不重建已有生命周期、证据、来源和审批系统，优先复用并扩展。

## 2. 用户、任务与商业假设

### 2.1 首批用户

- **主要用户**：5–30 人 Web/SaaS 团队的技术负责人、QA 和产品负责人，频繁合并 AI 生成代码。
- **购买动机假设**：减少回归执行与维护时间，提前发现合并后的业务错误，得到可追溯交付依据。必须通过付费意愿与试点数据验证。
- **协同用户**：开发者接收可复现缺陷；业务负责人裁决标准；管理员配置工具与授权。
- **首批不追求**：完全没有可运行环境/资料/负责人，却要求系统证明整个项目正确；或要求平台自行承担生产写入风险的项目。

### 2.2 核心任务（JTBD）

| ID | 用户任务 | 用户收到的可用结果 |
|---|---|---|
| J1 | “验收这次合并有没有破坏业务” | 固定版本、覆盖范围、失败/阻塞、证据、可批准的交付报告 |
| J2 | “这个流程我不熟，先帮我找风险” | 依据与候选风险、可复核的探索轨迹、待澄清问题 |
| J3 | “线上问题修好了，证明没有回归” | 沿用原标准、固定新构建、缺陷/修复对照与未验证项 |
| J4 | “给这个模块补有效测试” | 可审查的测试补丁、来源/性质说明、隔离执行及有效性结果 |
| J5 | “我们的登录/数据/工具比较特殊” | 可安装适配器及版本化 Harness，无需 fork 平台核心 |

### 2.3 产品洞察

- 开发者和模型都能生成测试代码，难点是**独立判断应该测什么、正确结果是什么，以及失败后该怎么继续**。
- 自动操作、测试设计、业务判定是三个不同问题；不能用点击成功替代验收通过。
- 通用性来自统一上下文/工具/执行协议和明确兼容范围，不来自一个万能提示词。
- 可靠性需要“知道何时不知道”：有用的阻塞报告优于没有依据的 PASS；同时必须降低无谓阻塞，不能靠拒绝所有任务获取安全指标。
- 产品差异要靠真实项目效果验证。来源治理和证据闭环是已投入的基础，不自动构成市场领先。

## 3. 产品成功的定义

北极星指标：**在冻结业务范围内，无人工修正执行过程而产出可复核结论的任务比例**，同时受缺陷检出率、误报率和覆盖完整性约束。

不能只优化“完成率”：故障时错误地判 PASS 会使完成率虚高。不能只优化“准确率”：把难例全部 BLOCKED 会使剩余样本看起来更准确。

发布候选门槛、分母、首败保留和对照实验详见 [EVALUATION](EVALUATION.md)。主要候选目标为：支持范围内流程完成率 ≥80%、已知业务缺陷召回 ≥85%、缺陷候选精确率 ≥90%、人工操作时间较人工基线减少 ≥50%。**均为目标，尚无达到证据**；试点前冻结门槛，未达标按失败记录，不能事后改分母。

初次资料裁决、环境授权属于启动成本，需单独记录；执行中的人工操作、补定位、改脚本、补模型输入计入介入，不能隐藏。

## 4. 支持范围与自主等级

### 4.1 2.0 必做兼容面

- Chromium Web：常见 SPA、表单/表格、弹窗、异步状态、跨页流程、多角色、刷新持久化、上传/下载、同源 iframe；跨源 iframe 必须显式授权其来源。
- DOM 定位优先，视觉用于 DOM 不足的控件、布局和 Canvas 候选操作；可验证文字/金额/权限尽量读取结构化值。
- HTTP API：请求模板、OpenAPI 导入、认证引用、状态/Schema/业务断言、UI/API 交叉核对。
- 代码：Node（npm/pnpm 锁文件）与 Python（声明支持的锁定依赖）的现有测试和候选测试生成。复杂 monorepo 必须选定服务与目录。
- 环境：已部署测试网址优先；自有运行器；明确受支持的 Node HTTP / Python ASGI + 可选 PostgreSQL 模板。多服务自定义部署需要经过审核的适配器。
- 数据：项目/任务命名空间、每角色账号、可审计资源台账、准备/核对/清理协议。

兼容矩阵必须细到登录方式、控件、语言、依赖、部署方式。未通过兼容测试的组合显示 experimental 或 unsupported，不用“支持 Web”概括全部网站。

### 4.2 自主等级

| 等级 | 允许行为 | 批准机制 |
|---|---|---|
| A0 调查 | 读取已授权资料、仓库、记录 | 项目授权；不执行业务写入 |
| A1 只读执行 | 登录后的已批准只读页面/API/日志检查 | 按任务范围批准；“GET”本身不是无副作用证明 |
| A2 沙箱业务测试 | 在测试环境和命名空间内创建/修改测试资源 | 一次批准动作范围、资源范围与预算；范围内无需每次点击审批 |
| A3 工程执行 | 隔离安装、测试、临时部署、生成测试补丁 | 审核过的运行模板；代码仓库补丁由人审阅 |

2.0 不自动批准生产写入、支付、真实消息发送或删除既有业务资源。检测这些动作形成待办并保存上下文。普通测试范围内可自主操作，避免每个动作都打断用户。

## 5. 核心旅程

### U1：给仓库 + PRD + 测试网址，验收一次发布

1. 用户粘贴仓库/网址；系统只读发现，固定 SHA，识别 PRD/接口/运行线索和缺口。
2. 若 PRD 在仓库内直接提议纳入，不重复上传；用户确认业务权威性与当前版本。
3. 系统构建“规则—风险—角色—状态—断言”覆盖地图；对冲突提最小必要问题。
4. 提议测试任务、支持范围、预计预算区间、账号/数据缺口；用户一次批准。
5. 准备环境与数据，运行前探测构建身份；执行期间按观察反馈调整操作。
6. 运行中只有越界、缺少业务依据、认证需人工或写入结果不明时暂停。
7. 用户查看缺陷卡片与复现；报告列完整分母、未执行范围和成本。
8. 修复后用原标准和固定新构建复测；“改需求”走新基线，不改写旧缺陷。

验收示例：审批阈值已批准为大于 5,000 元需主管审批，模型必须测边界、越权与刷新持久化；即使界面换了按钮名称，也只能调整操作方式，不能把阈值改成实际程序当前使用的值。

### U2：只有 Git 地址

先调查仓库资料和运行条件。发现可信候选 PRD 后进入 U1；没有业务依据时只提供工程检查、风险线索和待澄清问题。支持的服务可以提议隔离启动；无法启动说明具体依赖。不得把已有单测通过包装成“项目业务正确”。

### U3：自主探索一项业务

用户授权“测试工作区内的草稿创建与编辑，禁止发布/删除旧资源”。系统识别允许动作，生成带来源的假设，执行状态转移和反例，维护已探索/失败/未访问状态图。结束必须说明探索范围与未覆盖状态，不能“未发现问题=系统无缺陷”。

### U4：代码准确性检查

输入模块范围、PRD/接口约定与固定提交 → 识别可测试性质 → 生成候选测试补丁 → 隔离安装和运行 → 用已知缺陷或变异验证测试是否真的能失败 → 给出覆盖、漏测与补丁。源码可以指导入口和类型，不能成为唯一业务预期来源。未经审查，不改产品代码、不自动合并测试补丁。

### U5：组装自定义 Harness

技术用户安装一个接口/登录/数据/视觉适配器 → 契约自检 → 配置允许的能力和模型 → 用画布或表单组合 → 静态校验 → dry-run → 审阅动作范围 → 发布版本 → 团队从预设创建任务。新适配器验收不得改核心 dispatcher。

## 6. 功能需求与验收

优先级 P0=2.0 基础发布必需；P1=2.0 完整发布必需但排在基础循环后；P2=后续路线。P1 不是可默默省略项。

### 6.1 接入与业务上下文（CTX）

| ID | 优先级 | 要求 | 正反例验收 |
|---|---|---|---|
| CTX-01 | P0 | 合并仓库/网址/上传为一个接入任务，冻结来源与扫描范围 | 仓库内 PRD 可直接纳入；扫描失败不假定文件删除 |
| CTX-02 | P0 | 规划真实消费原文、批准规则、页面/接口线索和缺口 | 规划调用记录中可追溯实际片段；只有 hasDocuments 不算完成 |
| CTX-03 | P0 | 来源权威性、冲突、未解析、过期均进入覆盖地图 | 冲突不靠模型调和；LOW/UNPARSED 不直接成为确定标准 |
| CTX-04 | P0 | 按任务检索并记录选中/排除的资料版本与片段 | 检索无命中不得声称没有要求；覆盖不等于检索命中率 |
| CTX-05 | P1 | API 契约、设计图和代码线索可补充上下文 | 设计图可形成候选视觉预期；未批准推断不升级为硬标准 |
| CTX-06 | P1 | 上下文预算、摘要引用和跨块关系可审计 | 截断/压缩保留缺口；原文否定、条件、金额单位不能被摘要改写 |

### 6.2 测试策略与判定依据（DES）

| ID | 优先级 | 要求 | 正反例验收 |
|---|---|---|---|
| DES-01 | P0 | 六维覆盖：正常、边界、权限、多角色、状态、持久化；每项有依据或阻塞 | 缺权限矩阵时记 BLOCKED；不编造管理员权限 |
| DES-02 | P0 | 规则→风险→用例→断言双向关联，列未覆盖/不适用理由 | 重复生成同一用例不能提高覆盖率；不适用由有权人员确认 |
| DES-03 | P0 | 分离不可变业务判定契约 OracleSpec 与可调整操作计划 | 同一 oracleHash 下可改定位；改 expected 必须新批准版本 |
| DES-04 | P0 | 断言按确定性值、契约、视觉/语义候选区分 | 金额/状态优先代码校验；视觉低置信度进入复核而非 PASS |
| DES-05 | P1 | 决策表、边界/等价类、状态转移、性质/变形测试建议 | 生成性质须有来源或人工批准；不能仅复述实现得出预期 |
| DES-06 | P1 | 变化影响分析与测试优先级 | 排序不能静默删掉低分用例；未跑范围仍进最终分母 |

### 6.3 自主执行循环（LOOP）

| ID | 优先级 | 要求 | 正反例验收 |
|---|---|---|---|
| LOOP-01 | P0 | 持久化 Observe→Plan→Act→Verify→Adapt，每步有结构化决策和依据 | 实际观察改变下一动作；只执行一次生成的固定脚本不算通过 |
| LOOP-02 | P0 | 每次行动校验能力、权限、数据范围、角色、预算和当前构建 | 模型提出目录外工具拒绝；页面提示词不得改变授权 |
| LOOP-03 | P0 | 操作变化可自修复，业务标准不可自修复 | DOM 改名后可重新观察定位；不得删除失败断言/修改阈值 |
| LOOP-04 | P0 | 防空转、动作重复、振荡和无进展；明确结束条件 | 三次等价无进展后换策略或求助；禁止无限点同一按钮 |
| LOOP-05 | P0 | 外部写入意图、回执、未知结果对账、取消与恢复 | 写入后进程退出不重复创建订单；失联不能回到 PASS |
| LOOP-06 | P0 | 用户暂停/继续/接管/取消；活动预算与等待时间分离 | 人工门状态重启保留；取消后模型结果不得继续派发写入 |
| LOOP-07 | P1 | 输出可保存为回归资产，固定标准、数据策略和有效绑定 | 保存后在新实例复跑，不能依赖上次残留数据才通过 |
| LOOP-08 | P1 | 多角色会话、并发冲突与异步任务可编排 | 角色 A 操作后由 B 验证；重复提交/状态竞态保留时间线 |

### 6.4 可组装 Harness（HAR）

| ID | 优先级 | 要求 | 正反例验收 |
|---|---|---|---|
| HAR-01 | P0 | 注册式 SDK/协议，至少支持 TS 本地适配器与 Python 远程适配器 | 加一个新工具不修改核心调度；契约不匹配在安装阶段失败 |
| HAR-02 | P0 | 同能力多实例、类型化绑定、条件、子流程、有界 retry/repeat/map | 两个 HTTP 节点输出不串线；无界循环、循环引用拒绝 |
| HAR-03 | P0 | 模型/工具/环境/策略/判定/记忆以 HarnessProfile 固定版本组装 | 运行中升级插件不改变已有运行；撤销权限立即约束后续动作 |
| HAR-04 | P0 | dry-run、记录回放、故障注入和单节点调试 | 回放不访问真实外站/真实写入；凭据不可写进可分享包 |
| HAR-05 | P1 | 画布与表单两种视图，图来自同一 AST | 两视图来回切换不丢参数；键盘可完成编辑 |
| HAR-06 | P1 | MCP 适配桥：把选中的工具包装为受控能力 | 默认未授权工具不可用；远端 descriptions 不能提升权限；结果验证 |
| HAR-07 | P1 | 版本安装/禁用/升级/回滚与兼容矩阵 | 同时存在 v1/v2，运行 pin 正确；危险声明不完整不能发布 |

完整实体、生命周期和契约示例见 [HARNESS-SPEC](HARNESS-SPEC.md)。2.0 的“任意组装”是已注册且兼容的能力可以自由组合；不是允许不受控代码绕过平台。

## 7. 关键语义与不可混淆状态

- **业务结果**：PASS / FAIL / BLOCKED / REVIEW / NOT_EVALUATED；报告兼容现有契约，映射统一在 reporting 层。
- **任务生命周期**：排队、准备、执行、等待人工、暂停、完成、失败、取消。任务结束不等于业务通过。
- **操作结果**：成功、可确认失败、未知写入、取消、预算耗尽。未知写入先对账，不能当作没发生。
- **缺陷可信度**：候选、已复现、已人工确认、待调查、已修复验证。不同状态有不同展示和通知规则。
- **测试来源**：批准需求、接口契约、批准性质、模型假设、工程线索。模型假设不能未经批准升级为业务事实。
- **覆盖**：已选规则/风险/角色/状态的验证情况；分别显示业务、操作路径、代码行、探索范围，不能混成一个百分比。
- **自修复**：允许改变达到断言位置的操作策略；不允许改变断言期待、删断言、跳过失败用例或静默扩大权限。

## 8. 2.0 的判定可信链

```text
版本化原文 + 业务裁决 → RuleVersion → OracleSpec（批准并冻结）
                                          ↓
目标 + 当前观察 + 工具目录 + 有效记忆 → 操作计划 → 工具执行
                                          ↓
                              实际值 + EvidenceBundle
                                          ↓
                    程序化验证 / 有界语义复核 → 判定与缺口
```

Planner 不读取独立评测答案；不能仅靠运行页面当前表现生成预期。Judge 不因“任务快完成了”降低断言标准。模型自评“成功”仅为候选事实，最终由 verifier 结合证据检查。视觉/语义判断不能确定时保留 REVIEW，人工复核有单独审计。

## 9. 非功能要求

### 性能与容量

- 候选基准环境：8 vCPU / 16 GiB、独立数据库、2 个浏览器执行槽。目标 10 个活动任务，其中最多 2 个同时占用浏览器；其余排队、等待或执行轻量节点。发布前实测并公布硬件与配置。
- 非模型列表/详情 API 在该基准正常负载下 p95 <1 秒；事件到界面 p95 <2 秒；取消请求接收 p95 <1 秒，实际工具停止目标 <10 秒。远端工具无法停止时显示未确认，不能伪造取消完成。
- 每任务 maxSteps/maxWallClock/maxActiveTime/maxModelCalls/maxTokens/maxCost/maxResources；任一先到即停止后续派发。价格缺失时 cost 显示未知，不得按零处理。
- 最多三个不同恢复策略尝试是建议默认，项目可降低；写入重试必须满足对账规则，不能因为还有重试次数就重做。

### 可靠性与安全边界

- 每次发布执行预算/权限/来源/版本/幂等/未知写入/证据完整性回归。
- 文档、网页、仓库代码、MCP descriptions、工具输出都是不可信输入；模型不能扩大动作范围。
- 秘密仅引用并在实际需要时注入目标工具；模型、普通日志、回放包、报表不接收原值。
- 插件与仓库代码隔离；平台不向任务容器暴露 Docker socket 或数据库管理员连接。
- HTTPS/域名/出网/回调与项目授权保持服务器校验；UI 禁用不能代替 API 权限。
- 可访问性覆盖键盘、焦点、表单 label、状态不只靠颜色；桌面 1440、手机 390，无横向溢出。

## 10. 数据、架构与迁移

保留现有 TS 平台 + Python 智能服务，扩展共享契约。模型输出是建议，TS 平台拥有授权、持久化、队列和判定提交权；Python 负责智能规划、提取与排序。语言边界不能变成两份不一致业务规则。

新增概念：TaskSpec、OracleSpec、HarnessProfileVersion、CapabilityManifest、AdapterInstallation、AgentSession、StepAttempt、ActionIntent/Receipt、ObservationSnapshot、CoverageLedger、ContextManifest、ModelRoutePolicy、MemoryUse、EvaluationTrial。具体关系与迁移见 [ARCHITECTURE](ARCHITECTURE.md)。

1.0 已批准计划继续可执行。2.0 自适应计划保存为独立版本/模式，不改旧 acceptanceHash 的含义。新旧报告统一入口但标清执行模式。先按项目开关试点，旧任务不得在升级中切换执行器。

## 12. 商业化假设与运营需求

2.0 优先验证团队是否愿意为节约的人工时间、稳定回归和交付证据付费。自托管方案是首发，托管服务/团队治理/企业集成可以作为商业方向，但价格与套餐在验证前不固化。

每个试点记录：首次接入分钟、每周完成任务、有效缺陷、人工时间、运行费用、重复使用意愿、退出原因。试点提供方拥有业务资料，默认不用于训练；后续若收集评测样本必须单独授权。

托管多租户、SSO、计费、跨区域数据驻留、SLA 是商业部署独立工作包，不用“已有 projectId”宣称已经具备完整 SaaS 隔离。

## 13. 发布门与范围决策

- **2.0 Alpha**：新增适配器不改核心、一个完整自适应循环、原标准不可变、故障恢复通过；仅邀请试点，不宣称替代 QA。
- **2.0 Beta**：Web/API/代码候选测试、组合设计器、真实提供商、记忆/调查闭环接通；至少三个授权项目开始持续评测。
- **2.0 正式发布**：全部 P0/P1 验收完成，冻结效果基准达标，安装与真实客户连续运行通过。可延期发布，不把未完成 P1 改成 P2 以宣布完成。
- **长期目标**：更多语言与原生客户端、性能/安全专项、协作智能体。只有新增兼容证据后才能扩大宣传范围。

## 14. 依赖、风险与待确认

| 风险/依赖 | 处理 |
|---|---|
| 完整 PRD/角色/第二和第三项目缺失 | 同时继续通用代码；试点门保持未验，不用合成案例充数 |
| 模型偶发输出正确但长期不稳 | 保留每次输出与首败；同种子/同预算重复评测，记录波动 |
| 页面自修复把真实业务 bug 掩盖 | 操作与 Oracle 分离；变更差异审计，oracleHash 不变 |
| 开源引擎效果/许可/接口变化 | 固定版本与适配层、兼容测试；正式采用前确认许可证和依赖 |
| 用户配置复杂、第一次就放弃 | 支持矩阵、向导、预检查、最小待办；衡量 time-to-first-evidence |
| 预算与延迟不可控 | 逐步预算账本、低成本策略基线；没有数据前不承诺降本 |
| 测试依据本身错误 | 展示来源与冲突，业务裁决保留；模型不能代替产品负责人决定需求 |
| 项目许可证未确定 | 由权利人确认；首页暂不宣称已有某种开源授权 |

待业务确认：首批三个授权项目、目标角色矩阵、数据/操作范围、人工基线参与者、模型预算。缺失不阻塞独立模块开发，但阻塞对应真实效果发布门。
