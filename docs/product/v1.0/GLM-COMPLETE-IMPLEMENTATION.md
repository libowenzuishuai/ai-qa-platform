## R01｜Python 多文件 diff

算法顺序：输入完整性校验 → 同路径配对 → 未匹配文件的唯一哈希重命名 → 增删/不确定分组 → 可解析配对的片段比较 → 覆盖对账 → 确定性稳定排序。模型不参与确定性文件枚举和删除判断。

提供可在 checkout 中复现的旧/新目录夹具、输入校验和与预期结果；不依赖本人电脑路径。可使用 Dify 观察包派生合成夹具，标记 synthetic；不冒称新真实 PRD。

## R03｜长文档处理，包含下游完整性

**尚缺**：完整业务 PRD 审核、独立角色账号/矩阵、实际构建核验、第二真实项目及授权。先在进度文档明确这些条件，不承诺虚构交付日期。向用户一次性列最小缺口（项目/资料位置/网址/允许操作范围，密钥另走安全配置），继续不依赖它们的工作。

准备可导入的试点 manifest、脱敏资料、storage/校验和、批准记录、环境/构建、健康/隐藏缺陷/修复对照、评测脚本。合成夹具验证代码，但不能计入两个真实项目。无依据维度 BLOCKED 或经业务确认不适用，不强行六类全绿。

真实 Kimi 单独 opt-in：不默认 CI 调用、不打印凭据；记录输入哈希、实际模型/提示词/参数、每次请求用量、原始输出、首败与重试。断言范围覆盖来源、数值单位、跨页/跨块关系、遗漏、权限与状态，不只有关键词命中。自动检查不能命名为人工复核。

真实模型未通、部署不可达、资料未批准等只记具体门未验。保留模型失败记录，不能为获得通过而削弱要求。试点 ground truth 与 agent 执行环境隔离。

## R12｜独立复核、发布核验与交付

实现结束后从新提交独立检查：

1. 权限/来源/冻结版本/预算/幂等/取消/失联/错误码/证据与日志脱敏。
2. 所有新增异步任务无占位节点；真正调用生产能力；持久化和清理已连接。
3. 新契约两端一致，数据库迁移干净库与升级路径可运行，旧数据/报告兼容。
4. 页面、API、导出、回传结论同源；零分母、未批准、未知副作用和部分覆盖不能 PASS。
5. 运行与改动相关测试，再执行必要完整回归；测试总数、跳过、失败及外部未验分开记录。
6. 检查 Git 变更里是否含凭据、真实客户隐私、.env、备份、node_modules、录入的真实登录态；只提交可公开的脱敏证据。
7. 最终文档更新 implementation-status、部署 README、用户演示步骤、验收矩阵和剩余限制。代码检查必须引用文件/真实行为，不仅复述开发报告。
8. 正常提交/推送并核对远端 SHA；仓库规则要求 PR 时创建 PR 并附审阅依据，保护分支不绕过。最终报告写明 main 是否已合并，不能只推工作分支却称 main 完成。

## 工作包报告格式

每完成 Rxx 写入进度文档：

- 对应 PRD/验收条目、用户现在可做什么。
- commit、修改目录、迁移/契约变化与兼容性。
- 实际命令、通过/失败/跳过数量、日期、运行环境、证据路径。
- 组件真实性：mock、真实本地 HTTP/DB/浏览器、真实提供商、真实项目分别声明。
- 先失败后修复的关键反例；仍存在的风险/限制。
- 外部阻塞的具体条件，其他工作是否仍可继续。

## 最终回复模板

“代码状态：完成/未完成；发布状态：通过/未通过/部分待验。main 提交：……。R00–R12 完成表：……。实际测试：……。页面与可复现入口：……。未满足门槛：……。用户最少需要补充：……。”

若外部条件未齐：可以说“本轮代码与隔离验收已完成，真实发布还缺 X”，不可说“全部工作完成”。若仍有可独立完成的代码，继续实现，不以缺试点资料为由停掉代码收尾。
