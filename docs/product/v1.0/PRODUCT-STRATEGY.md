# AI QA：产品战略与商业验证

2026-09-20 · 创业方案工作稿 · 未进行客户访谈、付费验证或商标注册

## 1. 产品主张

**面向 AI 开发时代的软件验收平台。接入项目，说清测试目标，获得有依据、可复现的交付结论。**

长期愿景：承担团队从测试设计到缺陷复测的工作，让越来越少的人工操作覆盖更多交付风险。对外不承诺“替代所有测试人员”；近期卖点是把明确范围的验收可靠地做完。

核心购买理由是交付效率和可信结论：负责人知道哪里有问题、哪里还没有验证，以及下一步需要谁处理。

## 2. 对上一版的修正

- 产品中心从“采购系统的页面与用例”转为“团队的软件项目及每次变更”。采购只是后续评测样例之一。
- 从上传文件、批准规则、点执行等模块顺序，改为目标驱动任务。资料、规则、用例是可追溯资产，在需要时展开，不要求新用户先学懂全部术语。
- 接入仓库同时发现 README、PRD、OpenAPI、测试、构建配置；同一个文件无需重复上传。
- 有源码、只有网址、已有 CI 的项目都可进入统一工作流。对不支持的运行环境明确提供自有执行器接入或阻塞原因。
- “高端感”来自信息层次、状态可信、缺陷证据与省下的操作，不依赖大屏装饰、虚构质量分或多个智能体头像。

## 3. 客户与首个付费场景（待验证假设）

首批选择 5–30 人、频繁交付的 B2B SaaS / AI 应用团队：开发广泛使用 AI coding，产品负责人/技术负责人承担验收，已有测试环境，缺少持续回归能力。优先售卖“每次交付前，关键用户旅程的独立验收”。

- 购买者：技术负责人、研发负责人、QA 负责人。
- 每日使用者：测试工程师、开发者、产品经理。
- 触发时机：准备发版、多人合并、修改关键业务、修复缺陷后。
- 首次价值：连接现有测试环境和业务资料，得到一份可复现问题或范围明确的验收结果。
- 第一阶段不主攻移动端全矩阵、ERP 大规模定制、合规认证或无可运行环境的任意源码审计。

这只是初始获客聚焦。项目/来源/执行器/证据的数据结构保持跨业务、跨语言可扩展，不将行业模型写死。

## 4. 市场事实与差异化假设

截至 2026-09-20 阅读的官方资料：

| 官方资料 | 已能看到的能力 | 对本产品的启示 |
|---|---|---|
| [BrowserStack 需求生成用例](https://www.browserstack.com/docs/test-management/browserstack-ai/ai-generated-test-cases/from-different-inputs) | 从多类资料/链接生成用例并关联需求 | “PRD 生成用例”本身不足以构成长期差异 |
| [mabl](https://www.mabl.com/) | 强调自动创建、运行和维护测试的 agentic testing | 单纯自然语言操作浏览器不是独有卖点 |
| [QA Wolf](https://www.qawolf.com/) | 托管测试覆盖服务与 QA 人员参与 | 客户可能为可靠结果付费，而非只买工具入口 |

以上是厂商能力描述，未独立验证其准确率、价格、ROI；不据此宣称本产品领先。

我们的待验证差异：把产品要求、实际变更、测试执行与缺陷复测放在同一个可追溯流程；对“已证实失败”和“尚未验证”给出可解释结论；用户可以带入自己的环境、既有测试与执行器。

这需要实际项目数据证明。潜在壁垒是经授权、可复用的项目语义与稳定测试资产、定位维护经验、可复现缺陷评测集和团队协作融入度；不是模型名称或提示词数量。不能默认收集私有仓库训练模型。

## 5. 产品原则

1. **一次接入**：项目运行与资料发现同时进行，后续只补缺口。
2. **目标驱动**：用户说“验收本次订阅升级”，系统提出范围、依据、执行方式和预算。
3. **分层自主**：只读发现可自动；未知业务预期、高风险写入、范围扩展和预算提高需要决策；已批准基线常规回归不逐步打断。
4. **依据分级**：产品确认是验收依据；实现和已有测试是线索；推断要确认；冲突不自行裁决。
5. **能力显式**：不同执行器能做什么、不支持什么可见。不把浏览器发现当作后端权限验证。
6. **结果保守**：已执行和未执行分开，正式通过来自完整证据，而非模型自评。
7. **开放但有边界**：可替换模型、接入运行器、导出资产；任意插件不能改写冻结验收标准。

## 6. 商业形态与成本约束（假设，不是定价承诺）

- 开源核心：自托管项目管理、开放资产协议、基础运行器和报告，让团队能实际验证并保留资产。
- 托管团队版：按工作空间基础订阅 + 可解释的运行资源包收费；区分浏览器分钟、构建分钟、模型用量，超预算前提醒。
- 企业版：客户网络中的执行器、SSO、审计、保留策略与支持；先发现客户愿意付费的部署需求，再建设完整企业功能。
- 不按“生成用例数”作为主要计费单位，避免鼓励低质量堆量。私有部署也不意味着运行没有成本。
- 单任务贡献毛利需记录收入分摊、模型、浏览器/构建计算、存储、人工介入成本；未测量前不填毛利数字。
- 项目许可证与商业功能边界单独决策，本稿不修改仓库 LICENSE。

## 7. 获客与商业验证

先招募 3–5 个设计伙伴，来自至少两类业务；拿真实版本、资料与现有人工回归流程做对照。选择愿意开放测试环境、能给出验收负责人、能持续提供版本的团队。

试点步骤：基线访谈 → 同范围人工与平台对照 → 问题复现确认 → 连续多次交付使用 → 询问付费条件。记录失败接入与放弃原因，不能只展示成功案例。

对外内容：一条真实需求到可复现缺陷的完整演示；公开评测方法和限制；可导出的案例与本地运行方法。不能把 GitHub star 数当成交付价值或付费意愿。

关键待证假设：
- 接入和资料整理的人工成本足够低，第一次使用就能出现有用结果。
- 缺陷精确率足够高，团队愿意按报告采取行动。
- 在同一团队持续使用时，维护成本不会吞掉节省的回归时间。
- 用户愿意为连续验收与环境服务付费，而不只是试用免费的模型生成。

## 8. 指标与决策门槛

北极星：**每周被团队实际采纳、可追溯的交付评估数量**。采纳指负责人确认或进入既有交付流程，不能仅计生成报告。

配套：接入成功率、到首个可信结果时间、同范围人工介入分钟、缺陷报告精确率、独立隐藏缺陷集检出率、未验证范围、重复运行一致性、每次评估成本、团队周留存及付费转化。

产品发布门槛：至少两个不同业务项目完成需求到复测闭环；支持类型内的失败接入有明确解释；同一基线重复运行不隐藏首次失败。商业放量前还要验证实际团队重复使用与付费，不靠功能清单判断。
