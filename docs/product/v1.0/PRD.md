## 1. 产品使命与边界

**给出项目、资料和测试目标，获得独立于开发实现、带来源与执行证据的验收结论。**

服务高频交付、多人合并、使用 AI 编码的 Web/SaaS 团队。承担需求分析、测试设计、准备、执行、缺陷记录与复测工作。开发者是否已经运行单元测试，不影响平台独立依据 PRD 检查业务行为。

通用性体现在项目输入、业务模型、执行协议、工具组合和交付结论，不能解释为自动理解、部署和验证任意仓库。用户先得到当前支持范围及缺口，而不是一个未经验证的质量分。

### 1.1 用户与价值

| 用户 | 核心任务 | 产品输出 |
|---|---|---|
| 产品/业务负责人 | 确认需求、处理冲突、判断范围 | 原文关联的规则、未决问题、验收范围 |
| QA/技术负责人 | 建立验证策略、账号/数据/环境、审批计划 | 可执行的版本化方案、准备中心与可恢复工作流 |

| 查看者 | 理解交付风险 | 已验证/失败/未知、负责人和决策记录 |

首批目标为 5–30 人团队。商业 ROI、检出率和节省时间通过试点测量，不预先编造数字。

## 3. 信息架构与核心用户旅程

统一导航：**工作台、项目空间、产品上下文、测试任务、准备中心、执行中心、交付评估、能力与集成**。工作流属于任务的推进方式，避免用户在重复菜单间切换。

### 3.1 首次接入

粘贴 Git 地址/测试网址 → 固定版本并只读发现 → 显示资料、服务、既有测试与缺口 → 确认业务依据 → 提议测试范围 → 处理最少必要准备事项 → 批准后执行 → 报告。

仓库已含 PRD 时直接导入候选，无须重复上传。只有仓库没有环境时先做资料与工程分析；没有业务资料时只报告工程健康/探索候选。

### 3.2 需求变化与回归

手动同步或配置的 CI 事件 → 新上下文快照 → 多文件及原文差异 → 受影响规则/用例 → 人工确认保留、修订或补充依据 → 新基线与新计划 → 新任务。未完成必要复核显示缺口；不可偷偷缩小旧范围。

### 3.3 缺陷修复

查看失败及证据 → 指派处理人 → 新构建选择“按原标准复测” → 原始标准和计划固定 → 新结果关联旧 occurrence → 有权人员确认关闭。修改需求属于新基线，不能用它证明旧缺陷已修复。

### 3.4 目标驱动与组合

用户说明“验收本次权限和重复提交” → 系统列出可用工具、依据、范围、预算和准备缺口 → 根据项目批准策略确认 → 执行器推进节点 → 在缺少依据、权限、定位或写入结果不明时形成可处理待办。不能绕过规则/计划审批。

## 4. 项目接入与上下文（FR-CTX）

### FR-CTX-01 仓库与运行入口

支持规范化 GitHub HTTPS 仓库、固定完整提交 SHA、子目录、测试网址、自有运行器。保存 repo/commit/path/blobHash/取得时间；分支移动不修改已冻结快照。资料分类为 BUSINESS_CANDIDATE、API_CONTRACT、RUNTIME_CLUE、TEST_CLUE、UNCLASSIFIED。

扫描限定文件类型、单文件字节、总字节、文件数、路径、时间。截断、过滤、读取失败逐项记录。外链、子模块、符号链接不绕过边界；密钥文件不导入。资料中的提示词不是控制平台的指令。

私有 Git 首版仅 GitHub App 安装授权，明确安装及仓库范围；凭据由服务器安全保存且可撤销，页面只显示引用。回调 state、防跨项目绑定、撤销、过期、限流必须处理。未配置 GitHub App 时入口显示未配置，不能退回匿名或要求把 token 写入 URL。

### FR-CTX-02 来源可信等级

PRD/产品说明是候选业务依据；人工决定需作者/时间/引用；接口契约可支持结构约束。README、源码、既有测试默认仅为线索。模型推断不可自动批准为 EXPLICIT；资料冲突不能用时间新旧自动裁决。

支持原文预览、定位、质量、解析范围、版本历史、用途确认及冲突待办。拒绝伪造、跨项目、跨版本引用；UNPARSED 不支持规则，LOW 必须附核对事项。

### FR-CTX-03 多文件快照差异

新增共享契约，不强改当前单文件 SourceChangeReport。快照必须有同一仓库身份、固定提交、相同扫描范围及策略版本，以及扫描完整性；“在已声明范围内完整”和“整个仓库完整”必须区别。

文件条目：规范化相对 path、SHA-256 内容校验和、字节数、格式、取得/解析状态、可选真实 documentVersionId 与 bundle 引用。缺失条目只有在完整相同范围枚举时才可用于判定删除。

文件变化类型：added、removed、modified、renamed、unchanged、uncertain。同路径先配对；不同路径只在未匹配集合里按**字节内容哈希唯一的一对一对应**判纯重命名。重命名同时改内容、重复候选等输出 uncertain 或独立增删并明确未做重命名断言，禁止猜测业务连续性。

- 获取失败、权限拒绝、截断或扫描范围变化，不等于删除。拒绝比较不兼容范围，或产出明确 incomplete 及 unresolved；不能产出“无影响”。
- 同内容但解析质量/解析器变更，不得跳过解析影响检查；格式变化不得强行按旧 locator 配对。
- 复用 B2 同文件片段比较；新增/删除文件用真实单侧来源，不创建假空版本。
- 新增来源形成需求补充待办；删除来源传导至旧规则/用例；纯重命名须提示来源映射复核，不等于业务需求已改变。
- 每个输入文件必须有且仅有一个结果归属；模糊组显式记录多条候选，不能遗漏或重复消费文件。
- 变化、影响、决策与执行分别保存；保持旧任务/批准资产不可变。

### FR-CTX-04 长资料处理

解决的是**解析 → 分块 → 模型提取 → 跨块对账**，不能只增大 parse 上限。

保留完整规范化文档及原始 span ID；分块记录 documentVersionId、原文校验和、策略版本、chunkId、片段/块引用、上下文重叠范围与顺序。长 span 需要切片时增加局部引用和偏移映射，不能改写旧 span；偏移以 Unicode code point 计数，TS/Python 共享含中文和 emoji 的向量。

按标题、段落、表格边界优先；同一表头可作为上下文重复，但重复上下文不能算新覆盖。跨页表格无法可靠合并时保留位置并待确认。每个有效片段必须归属处理、上下文或明确阻塞；页数、字节、块数、视觉调用预算仍受控。

每个 chunk 固定输入和提示词版本；检查点可恢复；完成块不重复收费，结果不明的调用记录后明确重试政策。一个块失败不能被吞掉后发布“完整”规则集。模型输出截断视为失败，分配输出 token 预算，所有重试计入总预算。

规则合并保留准确原文、数值单位、角色和条件；跨块相同规则去重，冲突双向保留。合并自身也要分层有界，不得把所有块再次塞进单次超大请求。新增 ChunkCoverageReport 只说明输入处理覆盖，不宣称发现了全部业务规则。

## 5. 测试设计与任务（FR-DESIGN）

### FR-DESIGN-01 规则、用例与计划

规则建议须有来源/等级/条件/行为/预期/业务字段；冲突待决。用例覆盖正常、边界、权限、多角色、状态、持久化，并非所有项目都必有六类预期；无依据时列具体 blocker。

审批规则后生成用例，补全正式步骤 ID 和真实规则版本 ID；批准用例后观察环境生成计划，再批准执行。动作仅引用已观察 targetRef，断言与动作闭合；缺定位不能创造 selector。模型只建议，判定引擎确定性执行。

任务冻结资料、规则/用例/计划、环境 revision、构建、提示词/模型、预算、范围与排除原因。新版本不覆盖旧版本。重复回归可复用仍有效的批准资产，准备过期或环境变化必须重新核验。

### FR-DESIGN-02 基线变化与新增需求

保留/替换/新增/排除均留审计。已实现的变更复核只能替换既有资产；本轮补齐“新增来源 → 提取候选 → 批准新规则/用例 → 纳入新基线”。新基线完整继承未变范围，显式记录新增与排除；不自动改变旧任务或关闭旧缺陷。

必须有独立案例证明：删除必须检查的规则不能让原验收从 FAIL 变 PASS；新标准执行可形成自己的结论，且与旧标准不同。

### FR-DESIGN-03 待办与澄清

待办有原因、关联证据、处理人、解决方式、创建/处理时间。解释缺哪项资料/账号/范围，指向修复入口。取消、拒绝、审批过期、并发处理冲突均明确；处理结果不可覆盖旧决定，变更需新版本或新决策。

## 6. 准备与执行（FR-EXEC）

### FR-EXEC-01 准备中心

每环境/角色显示账号引用、登录配置、实际检查状态、检查时间、有效期和失效原因；验证码/MFA 进入人工处理。原始登录证据受限。密钥不进入表单返回、日志、截图展示、导出或模型上下文。

数据插件采用已注册 HTTP 模板、参数 schema、项目/运行命名空间、资源台账、清理职责与预算。并发运行互不清理资源。未知写入副作用不自动再发；404 可作为明确已清理，其他失败保留残留待办。

### FR-EXEC-02 Web 与 API

浏览器首版 Chromium，角色独立上下文；支持现有 TestPlan 动作与断言。网络策略覆盖重定向、表单、连接层和资源请求。后续诊断/截图也不能绕过边界。

API 通过服务端注册模板、认证引用、路径/参数校验与响应观察，补结构断言及业务字段断言；结构 schema 不能代替业务预期。金额、权限、幂等、异步等待及状态判定受正式规则约束。

### FR-EXEC-03 代码检查

首版支持 Node 内置测试、Vitest、Jest、Playwright 既有测试、pytest，以及配置明确的 lint/typecheck/build。包管理器按锁文件选择；多个冲突锁文件需显式选择，不随意安装最新版。通过注册适配器构造受控命令，不能开放任意 shell 表单。

隔离执行、资源/时间/网络预算、结构化测试/JUnit/覆盖率导入；零测试、报告损坏、退出码与报告矛盾不能 PASS。取消/失联/重复结果仍受 Run/runner 租约与证据归属约束。

代码健康与业务验收分别显示。运行既有测试不证明业务正确；可生成依据 PRD 的候选新测试，但不能默认把它写回被测仓库。

### FR-EXEC-04 自有运行器与受支持部署

保留认证、任务领取、租约、证据协议。任务容器不挂宿主文件、平台源码、平台密钥或 Docker socket；受信控制器按固定模板创建隔离资源。依赖安装也在隔离环境内，出口按阶段限制。

Node 服务模板配置工作目录、受支持的安装/构建/启动选择、端口、健康路径及可选独立数据库。部署产物、提交、实例核验对应；资源按任务清理，失败残留可查。配置不兼容明确 BLOCKED，不尝试任意命令拼接猜测。

## 7. 智能体运行框架（FR-AGENT）

### FR-AGENT-01 工具注册与版本化组合

复用现有 WorkflowRun/Node/Event，增加 CapabilityVersion 与 WorkflowTemplateVersion；禁止平行第二套调度器。

注册描述：key/version、输入/输出 schema、READ/WRITE 效果、所需角色与环境、预算类别、幂等策略、恢复策略、清理责任、状态。首批工具来自现有发现/解析/提取/用例/观察/准备/Web/API/代码/评估能力。

模板首版 DAG：有限节点、依赖、受限条件、明确输入映射。发布前校验循环、悬空引用、类型不匹配、缺权限和缺清理路径；条件不得 eval。版本发布不可变，运行固定版本；服务重启后按检查点恢复，不重放已知完成的写操作。

表单编辑器支持增删节点、依赖选择、参数表单、审批门和校验错误定位；发布后真实执行。只展示一个漂亮的节点列表不算完成。

### FR-AGENT-02 目标规划与受控探索

目标 → 工具选择/范围草案/依据/预算/缺口，不直接获得执行权限。仅已注册工具可选；结构和服务端语义校验拒绝不存在工具、跨项目、越权或预算超限。新探索只读优先，写入需已有明确授权范围。

探索观察保存来源/页面/环境版本；发现异常无业务依据时为 candidate finding，不是 FAIL。记忆包含项目、来源、版本、有效期/失效触发；过期、被撤销、跨项目记忆不可作为当前事实。

诊断区分事实、推测、建议下一步及置信限制；不能修正文案来改判已失败断言。允许有界重新观察定位建议，但新绑定须通过现有批准/版本机制，不能静默替换冻结计划。

## 8. 结果、缺陷与发布（FR-RESULT）

### FR-RESULT-01 结论合同

- 用例：PASS / FAIL / BLOCKED / REVIEW / NOT_RUN；平台 ERROR 单列。
- 严格验收：可信 FAIL 优先；无 FAIL 但有阻塞、未测、待复核、必需证据缺失、构建未核验/漂移，为 INCOMPLETE；非空批准范围全部满足才 PASS。
- 必测范围不能由 agent 删除。工程通过不能冲淡业务失败，mock 不能混进 real 通过结论。
- 通过率 PASS/选定数；执行率 (PASS+FAIL)/选定数；零分母 N/A。范围、分母、过滤条件和统计时间明确。
- 证据必须校验文件、哈希、归属及访问权限。分享或导出不能绕过原始受限证据授权。

### FR-RESULT-02 缺陷与决策

缺陷包含影响、严重度依据、来源、预期/实际、复现步骤、证据、构建、负责人、occurrence 和复测。人工关闭需理由，新结果不覆盖旧结果。

ReleaseDecision 独立存储 ACCEPT/REJECT/ACCEPT_WITH_RISK（仅决策，不是测试 verdict）、决策人、理由、范围、证据快照和时间。原 FAIL/INCOMPLETE 保持不变，决策修改追加新记录。

报告导出 JSON/Markdown，内容冻结并带版本、校验和、来源标记及统计口径；权限检查和受限证据处理一致。默认不生成公开证据链接。

## 9. 集成、治理与交付（FR-OPS）

### FR-OPS-01 CI 与仓库连接

GitHub webhook 验签、deliveryId 去重、仓库/项目绑定、分支过滤、限流、固定 SHA；重复事件不创建重复执行。过期/撤销授权明确失败。

受信分支可依配置触发已批准模板。外部分叉 PR 默认只读无敏感凭据/写 token，不执行可修改的流水线获取平台秘密。结果回传 GitHub Check 时使用同 SHA、冻结报告与必要的最小授权；仅在项目配置启用后回传。

### FR-OPS-02 权限、凭据与审计

自托管 1.0 以现有 ADMIN/LEAD/VIEWER 与服务端项目隔离为基础；本次新增入口全部受同策略约束。修改集成/模板发布属于 ADMIN；业务审批/运行/决策按 LEAD；VIEWER 只读且受限证据另鉴权。

私有连接所需凭据加密落库，密钥通过环境或受支持 secret provider 注入；说明轮换、撤销、备份恢复依赖。项目凭据不可提供给被测仓库或其他项目。平台日志统一 requestId、job/run、脱敏错误，默认不记录完整敏感输入。

记录真实用量，不知道单价时仅显示 token/时长。预算超限阻止下一动作；取消处理在途尾差。证据按项目保留策略清理，冻结报告所需证据缺失后报告应标明，不把失效旧报告继续当可验证 PASS；删除须验证作用域并有审计。

### FR-OPS-03 可安装与可维护

生产样式自托管 Compose 与开发配置分开；锁定依赖构建镜像，运行时不 install、不 migrate dev、不挂宿主 node_modules。镜像不包含 .env、测试答案、用户数据；Chromium、字体、Prisma 引擎和 Python 本地依赖在目标镜像内正确安装。

默认完整栈包含 postgres/redis/api/web/worker/intelligence；迁移为独立单次步骤，依赖健康后启动，缺配置有准确错误。demo 可选 profile，不进入业务生产默认配置。生产配置无通用默认账号/密码。

提供备份、恢复、升级、资源要求、故障排查。破坏性迁移另需审查；已有迁移不可改写，不能清空开发库解决冲突。干净环境与已有数据升级均真实验证；恢复不仅检查文件存在，还要读取恢复后的业务对象与证据引用。

## 10. 前端完整设计与验收

沿用 `design-system.ts`：深松绿导航、灰白工作区、白色卡片、低饱和绿主动作；琥珀与红表达待办/失败，均附文字。优先使用现有 SSR 组件，局部交互按需增强，不以重写 React 代替产品交付。

| 页面 | 首屏与核心交互 | 必须处理的状态 |
|---|---|---|
| 工作台 | 真实交付风险、待办、最近运行、进入项目 | 空数据、权限范围、统计失败/加载；禁止假实时数字 |
| 项目接入 | 单次输入 → 发现卡片 → 条件缺口 → 下一步 | 无 PRD、私库未授权、仓库不支持、发现部分成功 |
| 产品上下文 | 资料目录/原文/规则三栏，手机分面板；差异对比 | 未解析、低质量、长文进度、冲突、来源定位失效 |
| 测试任务 | 目标/范围/环境/预算逐步确认，业务用例优先 | 草稿、未批准、准备过期、计划失效 |
| 准备中心 | 每角色卡片、数据资源台账、检查/清理操作 | MFA、超时、残留、写入结果不明 |
| 执行中心 | 节点列表、真实事件时间线、证据面板 | 断线恢复、取消中、待人工、失败、完成 |
| 交付评估 | 结论/范围/失败/未知、复测与导出 | 零分母、模拟结果、失效证据、未核验构建 |
| 能力与集成 | 支持矩阵、连接状态、模板编辑/发布历史 | 未配置、撤销、版本不兼容、模板校验错误 |

所有列表服务端分页/筛选/授权范围统计；不以最近 100 条假装全量。核心流程选择可读名称，ID/JSON 只在诊断高级区。提交防重复、字段错误就地显示；禁用按钮解释原因。键盘可操作，焦点可见，表单 label，移动端 390px 不横向溢出，桌面 1440px 有效利用布局；表格允许独立横向滚动。

发布前真实浏览器走完整旅程；1440/390 截图逐页查看。原型必须明确标示示例数据，不能把原型按钮当产品已实现。

## 11. 契约、数据与架构约束

TS 负责权限/持久化/队列/冻结/审计/结果；Python 负责资料分析/差异/分块/建议；运行器负责受控执行。复用现有实体和生命周期。

新增契约按模块冻结：SnapshotDiff、ChunkManifest/Coverage、Capability/Template、GoalProposal/Memory、ReleaseDecision、Integration/CheckResult。Zod 是来源 → 导出 JSON Schema → 生成 Pydantic，生成文件不可手改；语义校验须两端共享向量证明。新增设计名不是已上线 API。

每项输入记录归属、版本、哈希、预算；输出先验证再发布；幂等键绑定规范化请求。任务创建与入队使用持久化恢复机制，避免事务成功后队列失败永挂。并发认领 CAS/租约，事件持久化序号续传；取消后过期响应不能复活任务。对有副作用操作明确已完成/未执行/结果不明，不用简单 retry 包装。

外部 API、模型、命令的错误按约定映射，不全部变 500；缺模型配置不退 mock；输出修复不改变业务原文、数字或标点。

## 13. 发布验收与完成定义

三个独立状态：**文档完成、代码验收完成、真实发布验收通过**。只有矩阵内对应门槛满足才升级状态，不能按文件数量或测试总数宣布全部完成。

- 每 R 包至少有一个用户正向场景和决定性的反例、真实组件证据、代码/测试路径与已知限制；mock/真实 HTTP/真实模型/真实客户各自注明。
- 共享契约/类型/构建/回归通过；测试跳过单列，现有 opt-in 不计为通过。低风险文字改动无需机械增测，关键行为必须验证。
- 干净安装与保留数据升级通过；故障恢复、跨项目拒绝、取消、预算、证据损坏、错误副作用不重放均有真实验证。
- 两个实际业务项目；一条已有网址路径、一条受支持仓库/自有运行器路径；至少一个完整 PRD 由人审核。正常/边界/权限/多角色/状态/持久化按真实适用范围验证，未适用附依据。
- 健康、隐蔽缺陷、修复三个构建/配置，测试 agent 不读 ground truth；原标准复测证明修复；保留首败和全部重试记录，不能只选最好一轮。
- 统计范围内报告假 PASS 必须为零：人为设置的失败、阻塞和缺失证据反例均不得通过。这是有限评测集验收门，不是产品对任意项目的零漏报承诺。
- 记录样本数、检出/误报/遗漏、重复稳定性、人工介入分钟、token/延迟与未知费用；样本不足明确，不把合成项目包装成第二客户。

Dify 现有资料仅 [脱敏观察包](../../../packages/contracts/fixtures/pilot-dify-v1/README.md) 和 [候选设计](../../delivery/pilot-dify-candidate-design.md)。可推进代码和受支持测试，不能补造完整 PRD、权限矩阵、第二角色或新资源授权。第二实际项目目前未提供，外部条件没有确定交付日期。

## 14. 后续版本路线

1.1：多租户组织/SSO/计费、托管连接器扩展、企业审计和高可用部署。1.2：拖拽复杂工作流、插件生态、受控并发智能体、视觉回归。专项版本：性能、安全、原生移动、AI agent 数据集与工具轨迹评测。每项需另定用户场景、成本与验收，不在本轮隐含承诺。
