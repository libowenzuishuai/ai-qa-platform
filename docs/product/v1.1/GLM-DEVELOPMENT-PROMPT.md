## P0-1 账号与准备中心

### 已有

`EnvironmentRuntime.secretRefs`、项目凭据命名空间、observation setup、环境 revision、buildProbe、`mission-readiness.ts` 和执行前准备页。保留这些能力。

### 实现

- 增加可保存的角色登录准备配置，首版支持 username/password 引用 + 可视化 fill/click 步骤和登录成功标识；沿用已有定位类型及白名单，不提供任意 eval/脚本。
- 普通用户选择角色、操作类型、目标、凭据用途；管理员只登记项目专属环境变量引用。首版不做明文密码入库或临时“加密”方案。
- “检查登录”作为可取消的有界异步作业，在独立 BrowserContext 执行，返回账号缺失/无效、定位失败、网站不可达、需交互认证等明确状态。检查成功保存时间、环境 revision、配置 hash、过期时间；不得把过期检查用于当前准备证明。
- 成功只表示本次账号检查通过；正式执行仍验证身份。验证码/MFA/SSO 不支持自动通过时返回人工处理状态，不循环猜测。
- 准备页分开显示：配置已登记、账号已验证、数据已准备、构建已核验；缺口要能跳到具体修复表单。
- 登录证据应屏蔽账号敏感字段；会话仅驻留受控执行侧并按任务销毁。无法可靠脱敏的原始 trace 不向普通用户发布。

### 主改

`packages/contracts`、`apps/api/src/routes-product.ts`/新准备服务、`apps/worker/src/observation.ts`/作业处理、`packages/test-runtime`、`apps/web/src/product.ts`。共享数据库字段按必要性新增。

### 验收

真实本地登录夹具：成功、错误密码、缺变量、未登录/过期、环境改版、取消/超时；跨项目拒绝；证据与模型输入无凭据；通过页面保存配置和检查，全程不手写 JSON。缺少真实外部账号不能宣称 Dify 自动登录验收通过。

## P0-2 数据准备与清理插件

### 已有

只有 demo fixture 与通用手工策略；声明 `dataSpec.strategy=fixture` 当前会被拒绝。这是能力未实现，不能删除拒绝逻辑来“修复”。

### 实现

- 最小插件接口：版本、参数 schema、支持的效果类型、`prepare`、`cleanup`、`inspect`，引用以项目注册 ID + 固定版本保存。先实现受限 HTTP 请求模板插件，参数仅数据，禁止任意脚本/任意网络地址。
- 资源台账记录 project/run/attempt、命名空间、外部资源引用、动作指纹、状态及证据。准备成功才进入业务执行；结果未知进入待核对，不能重建一份。
- 清理支持独立的有限预算：业务预算耗尽或取消后仍可清理自身资源；不能因此继续业务操作。准备一半失败也清理已登记资源。
- 相同清理请求幂等；404 等是否算“已清理”由已注册协议明确。清理失败保留残留资源和下一操作，不能静默 PASS。
- 支持管理员复核后再次清理具体资源，不接受全库/全环境清理参数。
- UI 从已注册能力选择准备/清理方式，参数由 schema 生成表单；展示插件未配置、资源残留和清理证据。

### 验收

真实第二接收站和隔离数据服务：两个并发 run 资源互不影响；准备中断、清理失败/超时、取消后清理、重复回调均有确定状态；不得清理另一个 run 资源；非法目标连接前拒绝；不盲目重放创建。

## P0-3 持久化任务编排（智能体 harness 第一版）

### 目标

用户选择项目并描述“本次验收目标”，系统生成可审阅范围，并推进已有解析/设计/执行链。首版按显式图执行，图节点调用已有能力；模型只能返回合法下一动作建议。

### 实现

- 在 Mission 之上或其执行实例中保存流程版本、固定输入引用、节点状态、检查点、budget、人工待办、工具调用账本。不要混淆可编辑 Mission 与不可变的单次运行。
- 状态至少能区分排队、工作中、等人确认、完成、失败、取消；对外 API 要有明确定义及允许迁移。已完成节点按结果引用续跑，不从头全部重放。
- 首个模板：资料解析 → 规则建议 → 规则批准门 → 用例建议 → 用例批准门 → 页面观察 → 计划建议/批准门 → 准备检查 → 执行 → 评估。复用已批准且版本匹配的资产时直接跳过对应生成门。
- 节点幂等键包含任务实例、流程版本、节点、输入 hash；记录请求/响应引用及调用效果。并发领取唯一，重启对账与取消可靠。
- 只读操作可按策略有限重试；写入 timeout/失联进入不确定状态，先 inspect 对账。没有幂等保证与资源证明时不得自动重放。
- 节点事件持久化后才推送，SSE 按游标恢复；保存的是工具行动摘要与依据，不要求保存模型私有思维链。
- 总预算同时约束时长、模型调用数、工具次数、token/成本可获得值；花费预估和真实用量分开。未知价格显示未知。
- 用户处理一个明确待办后才恢复对应版本的实例；重复确认不重复执行。工作流可停止、查看、继续，不能靠页面轮询维持状态。

### 验收

至少三处 kill/restart：解析后、等待批准时、写入动作结果回传前；前三者分别复用结果、等待人、进入核对，绝不重复写入。覆盖重复队列、旧租约回传、并发确认、预算耗尽、取消，以及事件断线续传。真实本地组件跑资料到报告路径，模型 mock/real 分开记录。

## P1 后续模块：P0 验收后逐项开始

### P1-1 能力目录与组合

版本化 `CapabilityDefinition`（input/output schema、effect、权限、资源、超时、清理契约）与 `WorkflowTemplateVersion`（节点、依赖、映射、预算）。注册实现需管理员控制；计划只能引用目录版本。发布时验证 DAG、循环/悬空引用、类型映射、未知 capability、READ/WRITE 边界。先完成可执行模板表单和节点详情，后做拖拽 UI。

### P1-2 探索、记忆、诊断

Python 输出目标分解/下一步建议；执行器始终独立检查。探索模式产候选发现，正式验收运行固定批准计划。定位修复只生成新绑定建议，不能改断言或把失败重写成功。记忆按项目、环境、来源版本隔离，有过期/删除/冲突处理；不能将历史模型推测变成业务要求。诊断区分产品失败、账号、环境、模型、脚本、证据缺口。

### P1-3 代码准确性与 CI

在现有 runner 协议增加受支持框架适配和静态检查结果类型；明确 lockfile/依赖安装协议、输出 schema、无测试不是 PASS。固定 commit，隔离源码执行，记录覆盖率与测试映射。Webhook 验签、eventId 去重、项目映射、结果回写权限分开；工程绿灯不能覆盖业务失败。任意仓库自动部署仍是独立模块。

### P1-4 决策路由（可选 TypeSafe）

先定义内部 `DecisionProvider` 输入候选列表与版本化状态、输出建议/模型信息/实际响应置信字段/使用量，默认复用现有网关。TypeSafe adapter 走专用 API，按官方文档实现，不假设 OpenAI 兼容。先旁路记录、不影响执行；无密钥时明确未启用。用同一批公开合成样本比较准确率、未知样本拒绝、校准、延迟和成本。权限、事实来源和最终 PASS 永不交给路由模型决定。

## 每个 PR / 交付的格式

1. 对应任务编号、解决的实际问题、变更目录和接口/迁移。
2. 实际运行的命令、通过/失败/跳过数及隔离组件；不要只说“全部通过”。
3. mock、真实模型、真实 UI、真实 Git 下载分别列证据。保留首次失败及修正，不能删除困难用例。
4. 未实现能力、外部阻塞、兼容范围和升级/回退方式。
5. 更新当前状态文档，不改写历史验收。独立提交后再合并；不强推、不重置别人的数据库或工作树。

相关检查按改动运行：`pnpm typecheck`、`pnpm contracts:check`、`pnpm test`、`pnpm test:intelligence`、受影响的真实浏览器/runner 测试、`pnpm test:phase1`。纯视觉改动无需重跑付费模型；修改执行/契约时必须跑语义和异常反例。
